# 요구사항

## 배경

팀에서 가볍게 쓸 TODO 웹앱이 필요합니다. 브라우저에서 할 일을 추가·완료·삭제하고
상태별로 걸러 볼 수 있어야 한다는 요청(이슈
[jhlim2-forks/symphony-todo-simulation#1](https://github.com/jhlim2-forks/symphony-todo-simulation/issues/1))에서
출발합니다. 아직 승인된 선행 근거 문서는 없으며, 이 문서가 첫 근거 문서입니다.

현재 저장소는 빈 화면만 제공하는 골격(`main.go`, `app.go`, `index.html`)이고
`/api/` 요청은 501을 돌려줍니다. 이 문서는 그 골격 위에 구현할 동작의 범위를 정의합니다.

사용자 시나리오는 다음과 같습니다.

1. 팀원이 브라우저로 앱을 열고 입력란에 할 일을 적은 뒤 Enter 키 또는 추가 버튼으로 등록합니다.
2. 진행한 항목은 완료로 표시하고, 필요 없어진 항목은 삭제합니다.
3. 전체 / 진행 중 / 완료 필터로 지금 볼 목록을 좁히고, 남은 할 일 개수를 확인합니다.
4. 페이지를 새로고침해도 목록은 그대로 유지되며, 서버를 다시 시작하면 목록이 비워진다는 점을 화면 안내로 알고 있습니다.

## 요구사항

- **REQ-01** 사용자는 입력란에 할 일 내용을 적고 Enter 키 또는 추가 버튼으로 할 일을 등록할 수 있다. 등록에 성공하면 입력란은 비워지고 새 항목이 목록에 나타난다.
- **REQ-02** 사용자는 목록의 각 항목을 완료 상태와 미완료 상태로 전환할 수 있으며, 전환 결과가 화면에 즉시 반영된다.
- **REQ-03** 사용자는 목록의 각 항목을 삭제할 수 있으며, 삭제된 항목은 목록에서 사라진다.
- **REQ-04** 화면은 전체 / 진행 중 / 완료 세 가지 필터를 제공하고, 선택한 필터에 해당하는 항목만 목록에 보여 준다. 현재 선택된 필터를 화면에서 구분할 수 있다.
- **REQ-05** 화면은 남은 할 일(미완료 항목) 개수를 표시하며, 추가·완료 전환·삭제 후 그 값이 갱신된다.
- **REQ-06** 보여 줄 항목이 없을 때는 빈 목록 안내 문구를 표시한다.
- **REQ-07** 입력값은 앞뒤 공백을 제거한 뒤 1자 이상 200자 이하만 허용한다. 허용 범위를 벗어난 입력은 등록하지 않고 화면에 오류 메시지를 표시한다.
- **REQ-08** 할 일 목록은 서버 메모리에 저장하며, 브라우저를 새로고침해도 목록이 유지된다.
- **REQ-09** 화면에는 서버를 다시 시작하면 목록이 초기화된다는 안내를 표시한다.
- **REQ-10** 추가·완료 전환·삭제·필터 전환을 키보드만으로 수행할 수 있다.
- **REQ-11** 할 일 입력란에는 용도를 설명하는 레이블이 연결되어 있다.
- **REQ-12** 화면은 너비 375px 모바일 화면에서 가로 스크롤 없이 사용할 수 있다.
- **REQ-13** 사용자가 입력한 내용은 HTML로 해석하지 않고 문자 그대로 표시한다.
- **REQ-14** `GET /api/todos`는 200과 함께 id 오름차순 JSON 배열을 반환하며, 항목이 없으면 빈 배열 `[]`을 반환한다.
- **REQ-15** `POST /api/todos`는 `{"text":"내용"}`을 받아 201과 함께 생성된 항목 `{"id":양의 정수,"text":"내용","completed":false}`를 반환한다.
- **REQ-16** `PATCH /api/todos/{id}`는 `{"completed":true}` 형태의 본문을 받아 200과 함께 변경된 전체 항목을 반환한다.
- **REQ-17** `DELETE /api/todos/{id}`는 204와 빈 본문을 반환한다.
- **REQ-18** 존재하지 않는 id에 대한 `PATCH`·`DELETE` 요청은 404를 반환한다.
- **REQ-19** 빈 text, 200자 초과 text, 잘못된 JSON, `completed` 누락 또는 boolean이 아닌 `completed`는 400을 반환한다. `POST`·`PATCH` 요청 본문은 전체가 정확히 하나의 JSON 객체여야 하며, 본문이 비었거나 객체가 아닌 JSON 값(배열·문자열·숫자·`true`·`false`·`null`)이거나 객체 뒤에 추가 데이터(쓰레기 문자, 두 번째 JSON 값)가 붙은 경우도 잘못된 JSON으로 보고 400을 반환한다. 최상위 `null` 본문은 JSON 문법상으로는 올바르지만 객체가 아니므로 거부한다.
- **REQ-20** 할 일 id는 양의 정수이며, 항목을 삭제한 뒤에도 그 id를 다시 사용하지 않는다.
- **REQ-21** `NewHandler()` 호출마다 서로 독립된 메모리 저장소를 사용하고, 동시에 들어오는 요청에도 안전하게 동작한다.
- **REQ-22** 구현은 Go 표준 라이브러리와 HTML/CSS/JavaScript만 사용하고 외부 패키지·CDN을 추가하지 않는다. `main.go`의 `-listen` 플래그와 `NewHandler() http.Handler` 시그니처를 유지한다.
- **REQ-23** `/`와 `/api/todos` 계열(`/api/todos`, `/api/todos/{id}`) 외의 정의되지 않은 경로에 대한 요청은 404를 반환한다. 루트 화면 문서는 경로가 정확히 `/`일 때만 반환하며 하위 경로에는 응답하지 않는다. 계약에 정의된 경로에 대한 미지원 메서드의 응답 코드는 이 요구사항에서 다루지 않는다.

## API 계약

항목(todo)의 JSON 표현은 `{"id":양의 정수,"text":"내용","completed":boolean}`입니다.
요청 본문은 JSON이며, `{id}`는 경로의 할 일 id입니다.

| 요청 | 응답 |
| --- | --- |
| `GET /api/todos` | 200, id 오름차순 JSON 배열(없으면 `[]`) |
| `POST /api/todos` `{"text":"내용"}` | 201, `{"id":양의 정수,"text":"내용","completed":false}` |
| `PATCH /api/todos/{id}` `{"completed":true}` | 200, 변경된 전체 항목 |
| `DELETE /api/todos/{id}` | 204, 빈 본문 |
| 없는 id의 `PATCH /api/todos/{id}`·`DELETE /api/todos/{id}` | 404 |
| 빈 text·200자 초과·잘못된 JSON·`completed` 누락/비boolean | 400 |
| 위 경로 외의 정의되지 않은 경로(`/foo`, `/api/unknown`, `/api/todos/{id}/extra` 등) | 404 |

- `POST /api/todos`의 `text`는 앞뒤 공백을 제거한 값으로 저장하며, 그 길이가 1~200자여야 합니다(REQ-07).
- `POST`·`PATCH`의 요청 본문은 전체가 정확히 하나의 JSON 객체여야 합니다. 빈 본문, 객체가 아닌 JSON 값(`[{"text":"a"}]`, `"a"`, `123`, `true`, `null`), 객체 뒤에 남은 추가 데이터(`{"text":"a"} garbage`, `{"text":"a"}{"text":"b"}` 등)는 모두 잘못된 JSON으로 400입니다(REQ-19).
- 최상위 `null` 본문도 400입니다. `null`은 JSON 문법 오류가 아니며 구조체·포인터·맵 어느 쪽으로 디코딩해도 오류 없이 성공하므로, 구현은 파싱 성공 여부와 별개로 "최상위 값이 객체인가"를 따로 검사해야 합니다(REQ-19, 설계의 「요청 본문 디코딩 규칙」).
- id는 양의 정수이고 삭제 후 재사용하지 않습니다(REQ-20).
- 오류 응답(400·404)의 본문 형식은 이 계약에서 규정하지 않으며, 클라이언트는 상태 코드로 판별합니다.
- 화면 문서(HTML)는 경로가 정확히 `/`일 때만 200으로 반환합니다. `/`와 `/api/todos` 계열 외의 정의되지 않은 경로는 404입니다(REQ-23). 404의 본문 형식은 규정하지 않습니다.
- 계약에 정의된 경로에 대한 미지원 메서드(예: `PUT /api/todos`)의 응답 코드는 이 계약에서 규정하지 않습니다(범위 밖).

## 범위 밖

이슈가 제외했거나 아직 결정하지 않은 항목으로, 이번 변경에서 다루지 않습니다.

- 로그인·회원 가입 등 인증과 사용자별 목록 분리
- 데이터베이스·파일을 사용하는 영구 저장, 서버 재시작 후 목록 복구
- 마감일, 우선순위, 태그
- 등록한 할 일의 텍스트 수정, 정렬 변경, 검색, 일괄 완료·일괄 삭제
- 오류 응답 본문의 고정 포맷과 오류 코드 체계(사용자용 404 화면 포함)
- 계약에 정의된 경로에 대한 미지원 메서드(예: `PUT /api/todos`)의 응답 코드는 정의하지 않음(이슈의 범위 결정). 정의되지 않은 경로의 404는 범위 안이며 REQ-23에서 다룬다
- 다국어 지원, 화면 테마 설정, 페이지네이션
