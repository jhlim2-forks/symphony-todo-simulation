# 설계

이 문서는 [requirements.md](requirements.md)의 요구사항을 구현하기 위한 설계입니다.
요구사항 ID는 `REQ-01`~`REQ-23`을 그대로 사용합니다.

## 구조

파일 구성은 저장소 제약(`docs/README.md`)을 그대로 따릅니다.

| 파일 | 역할 |
| --- | --- |
| `main.go` | `-listen` 플래그 파싱과 서버 기동. 변경하지 않습니다. |
| `app.go` | `NewHandler() http.Handler`, 메모리 저장소, `/api/todos` 핸들러 |
| `index.html` | 화면 마크업·스타일·스크립트(단일 파일, `//go:embed`로 포함) |

`app.go`의 구성 요소는 다음과 같습니다.

- `todo` 구조체: `ID int`, `Text string`, `Completed bool`. JSON 태그는 `id`, `text`, `completed`.
- `store` 구조체: `sync.Mutex`, `items map[int]todo`, `nextID int`(1부터 시작, 생성 시마다 1씩 증가하고 삭제 시에도 되돌리지 않음).
- `NewHandler()`는 호출될 때마다 새 `store`를 만들어 클로저로 묶은 `*http.ServeMux`를 반환합니다. 전역 변수에 저장소를 두지 않습니다.
- 저장소의 모든 읽기·쓰기는 뮤텍스 잠금 안에서 수행하고, 핸들러는 잠금 밖에서 JSON을 직렬화합니다.

라우팅은 Go 표준 라이브러리 `http.ServeMux`의 메서드·와일드카드 패턴을 사용합니다.

- `GET /api/todos`, `POST /api/todos`
- `PATCH /api/todos/{id}`, `DELETE /api/todos/{id}`
- `GET /{$}` — `index.html` 응답

루트는 반드시 `GET /{$}` 패턴으로 등록합니다. `GET /`로 등록하면 `/foo`, `/api/unknown`
같은 하위 경로까지 모두 매칭되어 화면 문서를 200으로 돌려주므로 REQ-23과 어긋납니다.
`{$}`는 경로가 정확히 `/`일 때만 매칭하므로, 위에 등록한 패턴에 해당하지 않는 경로는
`http.ServeMux`의 기본 동작에 따라 404가 됩니다. 표준 라이브러리 버전 등의 이유로
`{$}`를 쓸 수 없는 경우에는 `GET /` 핸들러 안에서 `r.URL.Path != "/"`이면
`http.NotFound`를 호출하는 명시적 경로 검사로 같은 동작을 보장합니다(둘 중 하나를 반드시 적용).

등록된 경로에 정의되지 않은 메서드로 들어온 요청은 `http.ServeMux`가 405로 응답합니다.

## API

응답 본문이 있는 경우 `Content-Type: application/json; charset=utf-8`을 설정합니다.

### 요청 본문 디코딩 규칙(POST·PATCH 공통)

REQ-19에 따라 요청 본문은 **전체가 정확히 하나의 JSON 객체**여야 합니다. 다음 절차를
`POST /api/todos`와 `PATCH /api/todos/{id}`가 공통으로 사용합니다.

1. `dec := json.NewDecoder(r.Body)`로 디코더를 만들고 `dec.Decode(&req)`로 첫 값을 읽습니다.
   오류가 나면(문법 오류, 타입 불일치, 빈 본문의 `io.EOF` 포함) 400입니다.
2. 디코딩된 값이 JSON 객체여야 합니다. 배열·문자열·숫자·`true`·`null` 등 객체가 아닌
   최상위 값은 400입니다(구조체로 디코딩하면 객체가 아닌 값은 1단계에서 오류가 됩니다).
3. 이어서 `dec.Decode(&json.RawMessage{})`를 한 번 더 호출하고 결과가 `io.EOF`가 아니면
   400입니다. 이 검사로 `{"text":"a"} garbage`처럼 뒤에 쓰레기가 붙은 본문과
   `{"text":"a"}{"text":"b"}`처럼 두 번째 JSON 값이 이어지는 본문을 모두 거부합니다.
   본문 끝의 공백·줄바꿈만 남은 경우는 `io.EOF`가 되므로 허용됩니다.
4. 1~3단계 중 하나라도 실패하면 저장소를 전혀 변경하지 않고 400으로 응답합니다.

`json.Unmarshal`이나 한 번의 `Decode`만 사용하는 구현은 3단계를 건너뛰어 잘못된 본문을
201/200으로 처리하므로 사용하지 않습니다.

### GET /api/todos

- 저장소의 모든 항목을 id 오름차순으로 정렬해 JSON 배열로 반환합니다(200).
- 항목이 없으면 `null`이 아니라 `[]`를 반환하도록 길이 0의 슬라이스를 사용합니다.

### POST /api/todos

- 본문 `{"text":"내용"}`을 위의 「요청 본문 디코딩 규칙」대로 디코딩합니다. 파싱 실패, 객체가 아닌 최상위 값, 객체 뒤에 남은 추가 데이터는 모두 400.
- `text`에 `strings.TrimSpace`를 적용하고, 길이를 문자(룬) 수로 셉니다. 0자이거나 200자를 초과하면 400.
- 새 id를 `nextID`에서 받아 항목을 저장하고 201과 생성된 항목 전체를 반환합니다.

### PATCH /api/todos/{id}

- 경로의 `{id}`를 정수로 해석합니다. 정수가 아니거나 저장소에 없으면 404.
- 본문 `{"completed":true|false}`를 위의 「요청 본문 디코딩 규칙」대로 디코딩합니다. 파싱 실패, 객체가 아닌 최상위 값, 객체 뒤에 남은 추가 데이터, `completed` 키 누락, boolean이 아닌 값이면 400. 누락과 비boolean을 구분하려면 `*bool` 또는 `json.RawMessage`로 받아 확인합니다.
- 본문 검증 순서는 디코딩 규칙 통과 → `completed` 확인이며, id가 없으면 404가 400보다 먼저 결정됩니다(AC-06).
- 해당 항목의 `completed`를 교체하고 200과 변경된 전체 항목을 반환합니다.

### DELETE /api/todos/{id}

- 경로의 `{id}`가 정수가 아니거나 저장소에 없으면 404.
- 항목을 지우고 204와 빈 본문을 반환합니다. `nextID`는 줄이지 않습니다.

### 오류 응답

- 상태 코드는 400 / 404 / 405(허용되지 않은 메서드)를 사용합니다. 본문 형식은 계약에 포함하지 않으므로 `http.Error`의 짧은 텍스트로 두고, 화면은 상태 코드로 메시지를 결정합니다.

## UI

`index.html` 한 파일에 마크업·스타일·스크립트를 둡니다. 화면 구성은 다음과 같습니다.

1. 제목과 안내 영역 — 서버 재시작 시 목록이 초기화된다는 문구를 상시 노출합니다.
2. 입력 영역 — `<label for="new-todo">`와 `<input id="new-todo">`, 추가 `<button>`. `<form>`의 submit으로 처리해 Enter 키와 버튼이 같은 경로를 쓰게 합니다.
3. 오류 메시지 영역 — 검증 실패나 요청 실패 시 입력란 아래에 문구를 표시하고, 다음 성공 시 지웁니다. `role="status"`로 보조 기술에도 전달합니다.
4. 필터 버튼 3개(전체 / 진행 중 / 완료) — 선택된 버튼은 `aria-pressed="true"`와 시각적 강조로 구분합니다. 필터는 화면 상태이며 서버에 보내지 않습니다.
5. 목록 `<ul>` — 항목마다 완료 체크박스, 텍스트, 삭제 버튼. 보여 줄 항목이 없으면 목록 대신 빈 목록 안내 문구를 표시합니다.
6. 남은 할 일 개수 — 미완료 항목 수를 목록 아래에 표시합니다.

동작 방식:

- 스크립트는 `fetch`로 API를 호출하고, 응답을 받은 뒤 화면 상태를 다시 그립니다. 최초 로드와 새로고침 시 `GET /api/todos`로 목록을 받아옵니다.
- 항목 텍스트는 `textContent`로만 넣고 `innerHTML`을 사용하지 않습니다.
- 클라이언트도 전송 전에 공백 제거와 1~200자 검사를 수행하지만, 최종 판단은 서버 응답(400)을 따릅니다.
- 체크박스·버튼 등 기본 포커스 가능한 요소만 사용하고, 클릭 전용 핸들러를 쓰지 않습니다.
- CSS는 단일 열 레이아웃에 `max-width`와 `box-sizing: border-box`를 사용해 375px 폭에서 가로 스크롤이 생기지 않게 합니다. 터치 대상은 충분한 높이를 둡니다.

## 수용 기준

### API

- **AC-01** (REQ-14) 빈 저장소에 `GET /api/todos`를 호출하면 200과 `[]`가 온다. 항목을 3개 만든 뒤 호출하면 id 오름차순 배열이 온다.
- **AC-02** (REQ-15) `POST /api/todos`에 `{"text":"보고서 작성"}`을 보내면 201과 `{"id":1,"text":"보고서 작성","completed":false}` 형태의 항목이 오고, 이후 `GET`에 그 항목이 포함된다.
- **AC-03** (REQ-07, REQ-15) `{"text":"  공백 제거  "}`로 생성한 항목의 `text`는 `"공백 제거"`다. 200자 입력은 201, 201자 입력은 400이다.
- **AC-04** (REQ-16) 미완료 항목에 `PATCH /api/todos/{id}` `{"completed":true}`를 보내면 200과 `completed`가 `true`인 전체 항목이 오고, `{"completed":false}`로 되돌릴 수 있다.
- **AC-05** (REQ-17) `DELETE /api/todos/{id}`는 204와 빈 본문을 반환하고, 이후 `GET`에서 그 항목이 사라진다.
- **AC-06** (REQ-18) 존재하지 않는 id로 `PATCH`·`DELETE`를 호출하면 404다. 삭제한 id로 다시 호출해도 404다.
- **AC-07** (REQ-19) `{"text":""}`, 공백만 있는 text, 201자 text, 깨진 JSON, `{}`(completed 누락), `{"completed":"true"}`는 모두 400이고 저장소 상태를 바꾸지 않는다.
- **AC-08** (REQ-20) 항목 3개를 만들고 마지막을 삭제한 뒤 새 항목을 만들면, 새 id는 삭제된 id와 다르고 기존 최대 id보다 크다. 모든 id는 양의 정수다.
- **AC-09** (REQ-21) `NewHandler()`를 두 번 호출해 각각에 항목을 넣으면 서로의 `GET` 결과에 영향을 주지 않는다. 하나의 핸들러에 동시 `POST`·`PATCH`·`DELETE`를 보내는 테스트를 `-race`로 실행해도 경고가 없고, 동시 생성한 항목의 id가 겹치지 않는다.
- **AC-10** (REQ-08) 항목을 만든 뒤 브라우저를 새로고침하면 목록이 그대로 보인다(서버 프로세스 유지 시).
- **AC-11** (REQ-22) `go build ./...`가 외부 의존성 없이 성공하고 `go.mod`에 require 블록이 없다. `index.html`에 외부 URL 참조가 없다. `go run . -listen 127.0.0.1:8099`가 해당 주소에서 응답하고 `NewHandler() http.Handler` 시그니처가 그대로다.

### 화면

- **AC-12** (REQ-01) 입력란에 내용을 적고 Enter 키를 누르면 항목이 추가되고 입력란이 비워진다. 추가 버튼으로도 같은 결과가 나온다.
- **AC-13** (REQ-02) 항목의 체크박스를 누르면 완료 표시로 바뀌고, 다시 누르면 미완료로 돌아온다. 새로고침 후에도 그 상태가 유지된다.
- **AC-14** (REQ-03) 항목의 삭제 버튼을 누르면 그 항목이 목록에서 사라지고, 새로고침 후에도 사라진 상태다.
- **AC-15** (REQ-04) 완료·미완료 항목이 섞인 목록에서 "진행 중"을 선택하면 미완료 항목만, "완료"를 선택하면 완료 항목만, "전체"를 선택하면 모두 보인다. 선택된 필터는 화면에서 구분된다.
- **AC-16** (REQ-05) 항목을 추가·삭제하거나 완료 상태를 바꾸면 남은 할 일 개수가 미완료 항목 수와 일치하게 갱신된다.
- **AC-17** (REQ-06) 항목이 하나도 없을 때와 선택한 필터에 해당하는 항목이 없을 때 빈 목록 안내 문구가 보인다.
- **AC-18** (REQ-07) 빈 입력이나 공백만 입력한 채 추가하면 항목이 생기지 않고 화면에 오류 메시지가 보인다. 201자를 입력해도 마찬가지이며, 올바른 입력으로 추가에 성공하면 오류 메시지가 사라진다.
- **AC-19** (REQ-09) 서버 재시작 시 목록이 초기화된다는 안내가 첫 화면에 보인다.
- **AC-20** (REQ-10) 마우스를 쓰지 않고 Tab·Shift+Tab·Enter·Space만으로 할 일 추가, 완료 전환, 삭제, 필터 전환을 모두 수행할 수 있고 포커스 위치가 보인다.
- **AC-21** (REQ-11) 할 일 입력란에 레이블이 연결되어 있어 레이블 텍스트를 클릭하면 입력란에 포커스가 간다.
- **AC-22** (REQ-12) 뷰포트 폭 375px에서 가로 스크롤이 생기지 않고 입력란·필터·목록·삭제 버튼이 모두 보이며 조작 가능하다.
- **AC-23** (REQ-13) `<img src=x onerror=alert(1)>`를 추가하면 그 문자열이 그대로 목록에 보이고 스크립트가 실행되지 않는다.

### 본문 디코딩과 라우팅

- **AC-24** (REQ-19) `POST /api/todos`에 다음 본문을 각각 보내면 모두 400이고 저장소에 항목이 생기지 않는다(직후 `GET /api/todos`가 `[]`): `{"text":"a"} garbage`, `{"text":"a"}{"text":"b"}`, `{"text":"a"} 123`, `{"text":"a"}null`, 빈 본문(`""`), `[{"text":"a"}]`, `"a"`. `{"text":"a"}` 뒤에 공백·줄바꿈만 있는 본문은 201이다.
- **AC-25** (REQ-19) 미완료 항목에 `PATCH /api/todos/{id}`로 `{"completed":true} garbage`와 `{"completed":true}{"completed":false}`를 보내면 각각 400이고, 해당 항목의 `completed`는 호출 전 값 그대로다. `{"completed":true}` 뒤에 줄바꿈만 있는 본문은 200이다.
- **AC-26** (REQ-23) `GET /`는 200과 화면 문서(HTML)를 반환한다. `GET /foo`, `GET /index.html`, `GET /api/unknown`, `GET /api/todos/1/extra`는 모두 404이며 HTML 화면 문서를 반환하지 않는다.

## 위험

| 위험 | 영향 | 대응 |
| --- | --- | --- |
| 서버 메모리 저장이라 재시작하면 목록이 사라진다 | 사용자가 데이터를 잃었다고 느낄 수 있다 | 화면 상단 안내로 사전 고지(REQ-09). 영구 저장은 범위 밖이며 필요해지면 별도 제안으로 다룬다 |
| 저장소 동시 접근으로 데이터 경쟁이 발생할 수 있다 | id 중복, 항목 유실 | 모든 접근을 뮤텍스로 보호하고 `-race` 동시성 테스트로 검증(AC-09) |
| 여러 탭·여러 사람이 동시에 쓰면 화면이 서로 어긋난다 | 다른 탭에서 삭제된 항목을 조작해 404가 뜬다 | 실시간 동기화는 범위 밖. 요청 실패 시 오류 메시지를 보여 주고 목록을 다시 불러온다 |
| 문자열 길이를 바이트로 세면 한글 입력이 200자 전에 거부된다 | 요구된 입력이 막힘 | 룬 단위로 길이를 센다(AC-03) |
