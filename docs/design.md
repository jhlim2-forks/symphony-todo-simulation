# 설계

## 구조

저장소 루트의 단일 Go 모듈(`module todo`)로 두고, Go 표준 라이브러리와 HTML/CSS/JavaScript만 사용합니다. 외부 모듈과 CDN은 쓰지 않습니다.

- `main.go`: `-listen` 플래그(기본값 `127.0.0.1:8091`)를 받아 HTTP 서버를 띄웁니다. 라우터 구성은 테스트에서 `net/http/httptest`로 바로 쓸 수 있도록 서버 실행과 분리합니다.
- 할 일 저장소: 메모리에만 보관합니다(REQ-09). 추가한 순서를 유지하는 슬라이스와 다음 ID 값을 함께 두고, 동시 요청에 대비해 뮤텍스로 보호합니다. ID는 1부터 1씩 증가하며 삭제한 ID는 재사용하지 않습니다.
- 마감일 보관: 할 일 한 건에 마감일 한 개를 둡니다(REQ-11). 값이 있을 때는 `YYYY-MM-DD` 형식의 표준 문자열로, 없을 때는 "없음"으로 구분해 보관하고(예: `*string` 또는 `*time.Time`), JSON으로 내보낼 때 없으면 `null`이 되게 합니다. 시각·시간대는 보관하지 않습니다.
- 일괄 삭제: 완료된 할 일을 한 번에 지우는 동작은 저장소에 함수 하나로 둡니다(REQ-15, REQ-17). 목록을 한 번 훑어 `done`이 `false`인 할 일만 원래 순서대로 남기고, 지운 개수를 함께 돌려줍니다. 뮤텍스로 보호한 한 번의 잠금 안에서 처리해 중간 상태가 보이지 않게 합니다. 다음 ID 값은 건드리지 않으므로 지운 ID는 재사용되지 않습니다.
- HTTP 핸들러: `/`는 화면 파일을 제공하고, `/api/todos`와 `/api/todos/{id}`, `/api/todos/completed`는 JSON API를 제공합니다. 경로를 가를 때 `/api/todos/completed`를 `/api/todos/{id}`보다 먼저 확인해, `completed`가 ID로 해석되어 `404 not_found`가 되지 않게 합니다. 제목 검증(공백 제거, 200자 제한)과 마감일 검증(형식과 실제 존재하는 날짜인지)은 저장소에 넣기 전에 각각 한 곳에서 수행하며, 추가(`POST`)와 수정(`PATCH`)이 같은 마감일 검증 함수를 함께 씁니다(REQ-12).
- `index.html`: 화면 한 파일. 서버가 `/`에서 제공하며 API를 호출해 목록을 다시 그립니다.

처리 흐름: 화면이 `GET /api/todos`로 목록을 받아 그리고, 추가·상태 변경·삭제 후에는 응답을 반영하거나 목록을 다시 불러와 화면과 서버 상태를 일치시킵니다.

## API

요청·응답 형식과 오류 코드는 `docs/requirements.md`의 `## API 계약`을 그대로 따릅니다. 구현에서 정하는 세부 사항은 다음과 같습니다.

- `GET /api/todos`
  - 추가한 순서대로 `todos` 배열을 반환합니다. 목록이 비어 있으면 `{"todos": []}`입니다(`null` 아님).
- `POST /api/todos`
  - 본문을 JSON으로 해석하고 `title`을 문자열로 읽습니다. 해석에 실패하거나 `title`이 문자열이 아니면 `400 invalid_json`입니다.
  - 제목의 앞뒤 공백(스페이스, 탭, 개행 등)을 제거합니다. 결과가 빈 문자열이면 `400 title_blank`입니다.
  - 제거 후 문자 수를 유니코드 코드 포인트(Go의 룬) 단위로 셉니다(`utf8.RuneCountInString`). 바이트 수로 세지 않으므로 한글·이모지 한 글자도 1자입니다(REQ-03). 200보다 크면 `400 title_too_long`이며, 정확히 200자는 허용합니다. 이어 붙인 이모지는 코드 포인트 수만큼 세며, 이를 한 글자로 묶는 처리는 표준 라이브러리만 쓰는 제약 때문에 하지 않습니다.
  - `due`는 생략할 수 있습니다. 생략했거나 `null`이면 마감일 없는 할 일로 추가합니다. 문자열이면 아래 마감일 검증을 거치고, 문자열도 `null`도 아닌 값(숫자·객체 등)이면 `400 invalid_json`입니다(REQ-11).
  - 성공하면 `201`과 추가된 할 일(`id`, `title`, `done: false`, `due`)을 반환합니다.
- 마감일 검증(`POST`와 `PATCH`가 공유)
  - 길이가 10이고 `YYYY-MM-DD` 모양인지 먼저 확인한 뒤 `time.Parse("2006-01-02", 값)`으로 해석합니다. 해석에 실패하면 `400 due_invalid`입니다. 이 방식은 `2026-02-30`, `2026-13-01`, 평년의 `2026-02-29`처럼 달력에 없는 날짜와 `2026-3-1` 같은 형식 오류를 모두 거절하고, 윤년의 `2024-02-29`는 통과시킵니다(REQ-12).
  - 통과한 값은 `YYYY-MM-DD` 표준 형식의 문자열로 다시 만들어 보관하므로, 저장된 값과 응답의 `due`는 항상 같은 형식입니다. 시간대 변환이나 "오늘"과의 비교는 하지 않으므로 과거 날짜도 그대로 받습니다.
  - 검증에 실패한 요청은 목록과 기존 마감일을 바꾸지 않습니다.
- `PATCH /api/todos/{id}`
  - 본문이 JSON이 아니면 `400 invalid_json`입니다.
  - 본문에 담긴 항목만 바꿉니다. `done`은 `true`/`false`, `due`는 날짜 문자열 또는 `null`입니다. `done`을 보냈으나 불리언이 아니면 `400 done_required`, `due`를 보냈으나 문자열도 `null`도 아니면 `400 invalid_json`, 날짜가 올바르지 않으면 `400 due_invalid`입니다.
  - `done`과 `due`가 둘 다 없으면 `400 nothing_to_update`이며 아무것도 바꾸지 않습니다. 본문에 키가 있었는지와 값이 `null`인지를 구분해야 하므로, 본문을 `map[string]json.RawMessage`로 먼저 읽어 키의 유무를 판단한 뒤 각 값을 해석합니다.
  - `due`에 날짜 문자열이 오면 그 날짜로 바꾸고, `null`이 오면 마감일을 지웁니다. 마감일 변경은 제목·완료 여부와 다른 할 일, 그리고 목록 순서를 바꾸지 않습니다(REQ-13, REQ-14).
  - `id`가 정수가 아니거나 해당 할 일이 없으면 `404 not_found`입니다.
  - 성공하면 `200`과 변경된 할 일을 반환합니다. 이미 같은 상태였다면 그대로 두고 `200`을 반환합니다.
  - 한 요청에 `done`과 `due`를 함께 보내면 둘 다 검증한 뒤 모두 적용합니다. 어느 하나라도 검증에 실패하면 아무것도 바꾸지 않고 오류를 반환합니다.
- `DELETE /api/todos/completed`
  - 완료된(`done: true`) 할 일을 모두 지우고 `200`과 `{"deleted": 지운 개수, "todos": [남은 할 일, ...]}`을 반환합니다. `todos`는 남은 전체 목록을 추가한 순서대로 담고, 남은 것이 없으면 `[]`입니다(`null` 아님).
  - 진행 중인 할 일은 한 건도 지우지 않고 제목·완료 여부·마감일과 서로의 순서를 그대로 둡니다(REQ-17).
  - 지울 완료 항목이 없으면 오류가 아니라 `200`과 `{"deleted": 0, "todos": [그대로인 목록]}`입니다. 같은 요청을 연달아 보내도 두 번째부터는 `deleted`가 `0`이 됩니다(REQ-18).
  - 요청 본문은 읽지 않습니다. 본문이 있어도 무시하므로 `invalid_json`은 쓰지 않습니다. 이 경로에 정의되지 않은 메서드는 `405 method_not_allowed`입니다.
- `DELETE /api/todos/{id}`
  - 성공하면 `204`(본문 없음)입니다. `id`가 정수가 아니거나 해당 할 일이 없으면 `404 not_found`입니다. `completed`는 위 경로에서 먼저 처리하므로 여기까지 오지 않습니다.
- 오류 응답은 모두 `{"error": {"code": ..., "message": ...}}` 형태이며, 오류가 발생한 요청은 목록을 바꾸지 않습니다.
- 오류 본문은 계약에 정의한 코드와 문구의 조합만 사용합니다. 코드별 한국어 문구를 한 곳(코드 → 문구 표)에서 만들고, 서버 내부 오류 메시지나 요청 본문의 내용을 `message`에 넣지 않습니다. 표에 없는 경로의 `404 not_found`와 정의되지 않은 메서드의 `405 method_not_allowed`도 같은 형식과 문구를 사용합니다.

## UI

`index.html` 한 페이지, 한국어 화면입니다(REQ-08). 위에서 아래로 다음 순서로 배치합니다.

1. 제목 영역: "할 일 목록".
2. 추가 영역: 제목 입력란(안내 문구 "할 일을 입력하세요"), 마감일 입력란, "추가" 버튼. 입력란이 비어 있거나 공백만 있으면 서버에 보내지 않고 "할 일 제목을 입력해 주세요."를 보여 줍니다. 추가에 성공하면 두 입력란을 모두 비웁니다.
   - 길이 판정의 기준은 서버의 유니코드 문자 수(REQ-03)입니다. 화면에서 미리 막을 때도 같은 기준으로 세며(예: `Array.from(제목).length`), 브라우저가 다른 단위로 세는 `maxlength` 속성에는 의존하지 않습니다. 200자를 넘기면 계약의 문구 "할 일 제목은 200자까지 입력할 수 있습니다."를 보여 줍니다.
   - 마감일 입력란은 `<label>마감일(선택)</label>`과 `<input type="date">`로 둡니다. 이 입력은 값이 있을 때 `YYYY-MM-DD` 문자열을 주므로 계약 형식과 그대로 맞습니다. 비워 두면 `due`를 보내지 않아 마감일 없는 할 일로 추가합니다(REQ-11). 날짜 입력을 지원하지 않는 브라우저에서는 글자 입력란으로 보이므로, 화면은 값을 고치지 않고 그대로 보내고 올바른지는 서버가 판단합니다(REQ-12). 서버가 `due_invalid`로 거절하면 계약의 문구를 오류 안내 영역에 보여 주고 목록은 그대로 둡니다.
3. 필터 자리: 추가 영역과 목록 사이에 필터가 들어갈 영역을 비워 둡니다. 이번 구현에서는 아무 요소도 넣지 않으며, 나중에 "전체 / 진행 중 / 완료" 선택을 이 자리에 추가합니다(REQ-10).
4. 일괄 삭제 영역: 필터 자리와 목록 사이에 "완료한 할 일 비우기" 버튼(`id="clear-completed"`) 하나만 둡니다(REQ-15).
   - 버튼을 누를 수 있는지는 화면이 마지막으로 그린 목록에서 `done`이 `true`인 개수로 정합니다. 0건이면 `disabled`로 두고, 1건 이상이면 풀어 줍니다. 목록을 다시 그릴 때마다 이 상태를 함께 갱신합니다. 처음 HTML에는 목록이 비어 있으므로 `disabled`로 적어 둡니다.
   - 누르면 먼저 확인 창을 띄웁니다(REQ-16). 브라우저가 제공하는 `window.confirm()`을 쓰고, 문구는 아래 템플릿의 `{count}`를 완료 항목 개수로 바꿔 만듭니다. 확인하면 `DELETE /api/todos/completed`를 보내고, 취소하면 아무 요청도 보내지 않고 화면을 그대로 둡니다.
   - 확인 창 문구는 오류 문구가 아니므로 `id="error-messages"`와 섞지 않고 별도 JSON 요소 한 곳에 둡니다. 스크립트는 이 요소를 읽어 쓰고, 같은 문구를 스크립트 안에 다시 적지 않습니다.

     ```html
     <script type="application/json" id="confirm-messages">
     {
       "clear_completed": "완료한 할 일 {count}개를 지웁니다. 지운 항목은 되살릴 수 없습니다. 지우시겠습니까?"
     }
     </script>
     ```

   - 응답을 받으면 본문의 `todos`로 목록을 다시 그려 서버 상태와 맞춥니다(REQ-18). `deleted` 값은 다시 그릴지 판단하는 데만 쓰고 화면 문구로는 보여 주지 않습니다(범위 밖). 성공 경로이므로 `clearError()`를 호출합니다. 실패하면 REQ-08의 기준에 따라 `showError(응답)`로 안내하고 목록은 그대로 둡니다.
5. 목록 영역: 추가한 순서대로 각 줄에 완료 체크박스, 제목, 마감일 표시, 마감일 수정 영역, "삭제" 버튼을 놓습니다. 완료된 할 일은 체크 상태로 표시하고 제목에 취소선을 넣습니다. 목록이 비어 있으면 "할 일이 없습니다."를 보여 줍니다.
   - 마감일 표시: `due`가 있으면 "마감일: 2026-03-01"처럼 날짜를 그대로 보여 주고, `null`이면 "마감일 없음"을 보여 줍니다(REQ-14). 마감일이 지났는지에 따라 달리 표시하지는 않습니다(범위 밖).
   - 마감일 수정: 각 줄에 `<input type="date">`와 "마감일 지우기" 버튼을 둡니다. 날짜를 고르면 그 줄의 할 일에 `PATCH {"due": "YYYY-MM-DD"}`를, "마감일 지우기"를 누르면 `PATCH {"due": null}`을 보냅니다(REQ-13). 마감일이 있는 할 일은 입력란의 초기값을 현재 마감일로 채우고, 없는 할 일은 비워 둡니다. "마감일 지우기" 버튼은 마감일이 있는 줄에만 둡니다.
   - 완료 체크박스는 전과 같이 `PATCH {"done": ...}`만 보내고, 마감일 수정은 `PATCH {"due": ...}`만 보냅니다. 한 번에 한 가지만 바꾸므로 `nothing_to_update`는 화면 조작에서는 생기지 않습니다.
6. 오류 안내 영역: 목록 아래 한 곳에 `id="error"`인 빈 요소로 둡니다. 보여 줄 문구는 다음 기준으로 정합니다.
   - 응답 본문이 계약의 오류 형식(`error.code`, `error.message`)이고 `code`가 계약에 정의된 값이면, 그 코드에 해당하는 계약의 한국어 문구를 보여 줍니다.
   - 그 밖의 경우(본문 형식이 다름, 정의되지 않은 코드, 본문을 JSON으로 해석할 수 없음, 통신 실패)에는 화면이 가진 한국어 기본 문구 "요청을 처리할 수 없습니다. 잠시 후 다시 시도해 주세요."를 보여 줍니다.
   - 어느 경우에도 응답 본문을 그대로 덧붙이거나 이어서 보여 주지 않습니다. 이어지는 요청이 성공하면 이 영역을 비웁니다.
   - 위 기준 중 "어떤 코드에 어떤 문구를 쓰는가"는 기계가 그대로 읽어 대조할 수 있는 형태로 둡니다. `index.html`에 아래와 같이 JSON 한 덩어리를 담은 요소를 한 곳만 두고, 스크립트는 화면을 그리기 전에 이 요소를 읽어 `ERROR_MESSAGES`와 `DEFAULT_ERROR_MESSAGE`로 씁니다. 같은 문구를 스크립트 안에 다시 적지 않습니다.

     ```html
     <script type="application/json" id="error-messages">
     {
       "default": "요청을 처리할 수 없습니다. 잠시 후 다시 시도해 주세요.",
       "codes": {
         "invalid_json": "요청 형식이 올바르지 않습니다.",
         "title_blank": "할 일 제목을 입력해 주세요.",
         "title_too_long": "할 일 제목은 200자까지 입력할 수 있습니다.",
         "done_required": "완료 여부(done)를 true 또는 false로 보내 주세요.",
         "due_invalid": "마감일은 2026-03-01처럼 실제로 있는 날짜로 입력해 주세요.",
         "nothing_to_update": "바꿀 내용을 보내 주세요. 완료 여부(done) 또는 마감일(due)이 필요합니다.",
         "not_found": "해당 할 일을 찾을 수 없습니다.",
         "method_not_allowed": "허용되지 않은 요청 방식입니다."
       }
     }
     </script>
     ```

   - 문구 표시는 `showError(응답)` 한 함수만, 비우기는 `clearError()` 한 함수만 담당합니다. `showError`는 `ERROR_MESSAGES`에서 찾은 문구를, 찾지 못하면 `DEFAULT_ERROR_MESSAGE`를 오류 영역의 텍스트로 넣습니다(응답 본문을 덧붙이지 않음). 목록 불러오기, 추가, 상태 변경, 삭제, 완료 항목 일괄 삭제의 성공 처리 경로는 모두 `clearError()`를 호출합니다.
   - 확인 방법과 그 한계: 프로젝트 제약상 테스트는 브라우저 없이 `net/http/httptest`로만 실행하므로, 화면 동작을 눌러 보며 확인하는 자동 검사는 두지 않습니다. 대신 ① 위 JSON 덩어리는 서버가 `/`에서 돌려주는 본문에서 꺼내 `encoding/json`으로 해석한 뒤 계약의 코드·문구와 정확히 같은지 대조하고, ② 서버가 실제로 돌려주는 오류 응답의 코드·문구도 같은 기준으로 대조해, 화면에 보일 문구와 서버가 보내는 문구가 어긋나지 않음을 자동으로 보장합니다. ③ 그 문구가 실제 브라우저 화면에 그려지는지, 성공 후 안내가 비워지는지 같은 실행 시점 동작은 자동으로 확인하지 못하므로, 구현 PR에서 사람이 한 번 눌러 보고 확인하는 항목으로 둡니다(수용 기준의 REQ-08 참고).

조작은 체크박스 변경 시 `PATCH`, "삭제" 클릭 시 `DELETE /api/todos/{id}`, "완료한 할 일 비우기" 확인 시 `DELETE /api/todos/completed`를 호출하고, 응답을 받아 목록을 다시 그립니다. 제목은 그대로 텍스트로 표시해 HTML로 해석되지 않게 합니다.

## 수용 기준

- **REQ-01**: 빈 목록에서 `POST /api/todos`에 `{"title": "장보기"}`를 보내면 `201`과 `{"id": 1, "title": "장보기", "done": false, "due": null}`을 받고, 이어진 `GET /api/todos`에 그 할 일이 보인다. 한 번 더 추가하면 `id`가 2가 된다.
- **REQ-02**: `{"title": "  장보기  "}`로 추가하면 저장된 `title`이 `"장보기"`다. `{"title": ""}`와 `{"title": "   "}`는 `400 title_blank`이고, 이후 `GET /api/todos`의 목록 길이가 늘지 않는다.
- **REQ-03**: 영문자 200자 제목은 `201`로 추가되고, 201자 제목은 `400 title_too_long`이며 목록이 늘지 않는다. 한글 "가"를 200번 반복한 제목(바이트로는 600바이트)도 `201`로 추가되고 저장된 `title`의 문자 수가 200이며, 201번 반복한 제목은 `400 title_too_long`이고 `GET /api/todos`의 목록 길이가 늘지 않는다. 이모지 "🙂" 200개로 된 제목도 같은 기준으로 `201`로 추가된다.
- **REQ-04**: "가", "나", "다"를 순서대로 추가한 뒤 `GET /api/todos`의 순서가 "가", "나", "다"다. "가"를 완료로 바꾸고 다시 해제해도 순서가 그대로다.
- **REQ-05**: 추가한 할 일에 `PATCH {"done": true}`를 보내면 `200`과 `done: true`를 받고 목록에도 반영된다. 이어서 `{"done": false}`를 보내면 `done: false`가 된다. `{"done": true}`를 두 번 보내도 `200`이고 `done: true`를 유지한다.
- **REQ-06**: 세 건 중 두 번째를 `DELETE`하면 `204`를 받고, `GET /api/todos`에는 첫 번째와 세 번째가 원래 순서와 완료 상태로 남는다. 같은 ID를 다시 `DELETE`하면 `404 not_found`다.
- **REQ-07**: 없는 ID(예: 999)와 정수가 아닌 ID(예: `abc`)로 `PATCH` 또는 `DELETE`를 보내면 `404 not_found`이고, `GET /api/todos` 결과가 요청 전과 같다.
- **REQ-08**: 브라우저를 띄우는 검사는 프로젝트 제약상 둘 수 없으므로, 확인할 수 있는 범위를 아래와 같이 나눠 둔다.

  (가) 자동 검사로 확인하는 것
  - `GET /`이 `200`과 HTML을 반환하고, 그 HTML에 제목 입력란, 마감일 입력란, "추가" 버튼, 목록 영역, 오류 안내 영역(`id="error"`, 처음에는 빈 상태)이 있으며 화면 문구가 한국어다.
  - HTML에서 `id="error-messages"`인 JSON 요소를 꺼내 `encoding/json`으로 해석하면, `codes`가 계약의 여덟 코드 `invalid_json`, `title_blank`, `title_too_long`, `done_required`, `due_invalid`, `nothing_to_update`, `not_found`, `method_not_allowed`만 키로 가지며 각 값이 계약의 한국어 문구("요청 형식이 올바르지 않습니다.", "할 일 제목을 입력해 주세요.", "할 일 제목은 200자까지 입력할 수 있습니다.", "완료 여부(done)를 true 또는 false로 보내 주세요.", "마감일은 2026-03-01처럼 실제로 있는 날짜로 입력해 주세요.", "바꿀 내용을 보내 주세요. 완료 여부(done) 또는 마감일(due)이 필요합니다.", "해당 할 일을 찾을 수 없습니다.", "허용되지 않은 요청 방식입니다.")와 글자 그대로 같다. `default`는 "요청을 처리할 수 없습니다. 잠시 후 다시 시도해 주세요."다.
  - 서버가 돌려주는 오류 응답의 코드·문구가 같은 표와 글자 그대로 일치한다. 예: `POST /api/todos`에 JSON이 아닌 본문을 보내면 `{"error": {"code": "invalid_json", "message": "요청 형식이 올바르지 않습니다."}}`, 정의되지 않은 메서드 요청(예: `PUT /api/todos`)은 `405`와 `{"error": {"code": "method_not_allowed", "message": "허용되지 않은 요청 방식입니다."}}`를 반환한다. 이로써 화면에 보일 문구와 서버가 보내는 문구가 어긋나지 않음을 보장한다.
  - HTML에 적힌 오류 문구는 위 JSON 요소 안의 문구뿐이고, 스크립트 안에 같은 문구를 다시 적은 곳이 없다. `id="confirm-messages"`의 확인 창 문구(REQ-16)는 오류 문구가 아니므로 이 대조 대상이 아니며, `id="error-messages"` 안에 들어가지도 않는다.

  (나) 자동으로 확인하지 않는 것(확인 범위 밖, 구현 PR에서 사람이 눌러 보고 확인)
  - 오류가 났을 때 그 문구가 실제로 오류 안내 영역에 그려지는지.
  - 계약에 없는 응답·해석 실패·통신 실패일 때 기본 문구가 그려지는지.
  - 목록 불러오기, 추가, 상태 변경, 삭제, 완료 항목 일괄 삭제가 성공한 뒤 오류 안내가 비워지는지.

  (나)는 브라우저가 스크립트를 실행해야 알 수 있어 자동 검사로 다루지 않는다. 대신 틀릴 여지를 줄이려고 화면 쪽 구현을 다음으로 고정하고, 이 구조가 지켜졌는지는 구현 PR의 코드 검토에서 확인한다: 문구를 넣는 곳은 `showError` 한 곳, 비우는 곳은 `clearError` 한 곳이며, 응답 본문을 문구에 이어 붙이지 않고, 다섯 가지 성공 처리 경로가 모두 `clearError()`를 호출한다.
- **REQ-09**: 저장소를 새로 만든 상태(서버 재시작과 같음)에서 `GET /api/todos`가 `200`과 `{"todos": []}`를 반환한다.
- **REQ-10**: `index.html`에서 필터가 들어갈 영역이 추가 영역과 목록 영역 사이에 한 곳 있고, 그 안에 "전체 / 진행 중 / 완료"를 고르는 요소가 없어 목록을 걸러 볼 수 없다(같은 자리에 있는 "완료한 할 일 비우기" 버튼은 필터 영역 안이 아니라 별도 영역에 있다). `GET /api/todos`는 필터 조건을 받지 않고 언제나 전체 목록을 추가한 순서대로 반환한다.
- **REQ-11**: `POST /api/todos`에 `{"title": "장보기", "due": "2026-03-01"}`을 보내면 `201`과 `due`가 `"2026-03-01"`인 할 일을 받고, `GET /api/todos`에도 같은 값이 보인다. `{"title": "청소"}`처럼 `due`를 생략하거나 `{"title": "청소", "due": null}`로 보내면 `201`이고 응답과 목록의 `due`가 `null`이다(키가 빠지지 않는다). `due`에 숫자나 객체를 보내면 `400 invalid_json`이고 목록이 늘지 않는다.
- **REQ-12**: `POST /api/todos`에 `due`를 `"2026-02-30"`, `"2026-13-01"`, `"2026-02-29"`, `"2026-3-1"`, `"03/01/2026"`, `"2026-03-01T10:00:00Z"`로 각각 보내면 모두 `400 due_invalid`이고 `GET /api/todos`의 목록 길이가 늘지 않는다. `"2024-02-29"`와 `"2020-01-01"`(과거 날짜)은 `201`로 추가되고 응답의 `due`가 보낸 값과 같다. 마감일이 `"2026-03-01"`인 할 일에 `PATCH {"due": "2026-02-30"}`을 보내면 `400 due_invalid`이고 그 할 일의 `due`는 `"2026-03-01"`로 남는다.
- **REQ-13**: `due`가 `null`인 할 일에 `PATCH {"due": "2026-03-01"}`을 보내면 `200`과 `due: "2026-03-01"`을 받는다. 이어서 `PATCH {"due": "2026-04-02"}`를 보내면 `due`가 `"2026-04-02"`로 바뀌고, `PATCH {"due": null}`을 보내면 `due`가 `null`이 된다. 이 과정에서 그 할 일의 `title`과 `done`은 바뀌지 않고 다른 할 일의 `due`도 그대로다. 마감일만 보낸 `PATCH`는 `done`을 바꾸지 않고, `done`만 보낸 `PATCH`는 `due`를 바꾸지 않는다. `PATCH {}`는 `400 nothing_to_update`이고 아무것도 바뀌지 않으며, 없는 ID로 보낸 `PATCH {"due": "2026-03-01"}`은 `404 not_found`다.
- **REQ-14**: `GET /api/todos`의 각 할 일에 `due` 항목이 있고, 마감일이 있는 할 일은 날짜 문자열, 없는 할 일은 `null`이다. `GET /`이 돌려주는 HTML에 각 줄의 마감일을 보여 줄 자리와 마감일이 없을 때 쓰는 한국어 문구("마감일 없음"), 마감일을 바꾸는 날짜 입력란, "마감일 지우기" 버튼이 있다. 세 건을 추가한 뒤 두 번째 할 일의 마감일을 넣고 바꾸고 지워도 `GET /api/todos`의 순서가 처음 추가한 순서와 같다. 각 줄에 실제로 마감일이 그려지는지는 REQ-08의 (나)와 같은 이유로 구현 PR에서 사람이 확인한다.
- **REQ-15**: `GET /`이 돌려주는 HTML에 `id="clear-completed"`인 버튼이 한 개만 있고, 문구가 한국어("완료한 할 일 비우기")이며, 처음 상태에서는 `disabled`로 적혀 있다(목록이 비어 있으므로 지울 완료 항목이 없다). 완료 항목이 생기면 버튼이 풀리고 0건이 되면 다시 잠기는 것은 브라우저가 스크립트를 실행해야 알 수 있어, REQ-08의 (나)와 같이 구현 PR에서 사람이 눌러 보고 확인한다. 서버 쪽에서는 `DELETE /api/todos/completed`가 있는 경로이고 `GET /api/todos/completed`가 `405 method_not_allowed`임을 확인한다.
- **REQ-16**: HTML에서 `id="confirm-messages"`인 JSON 요소를 꺼내 `encoding/json`으로 해석하면 `clear_completed` 키가 있고, 그 값이 한국어 문구이며 개수를 끼워 넣을 자리 `{count}`를 정확히 한 번 담고 있다. 이 문구는 `id="error-messages"`에 들어 있지 않다. 확인 창이 실제로 뜨는지, 지워질 개수가 맞게 보이는지, 취소를 누르면 요청이 가지 않고 목록이 그대로인지는 브라우저가 필요한 동작이므로 REQ-08의 (나)와 같이 구현 PR에서 사람이 눌러 보고 확인한다. 서버 쪽에서는 확인 창을 거치지 않은 요청도 그대로 처리하므로(화면만의 절차임) 별도 검사를 두지 않는다.
- **REQ-17**: "가"(완료), "나"(진행 중), "다"(완료), "라"(진행 중)를 순서대로 추가하고 "가"와 "다"만 `PATCH {"done": true}`로 완료한 뒤 `DELETE /api/todos/completed`를 보내면 `200`과 `deleted: 2`를 받고, 응답의 `todos`와 이어진 `GET /api/todos`에 "나", "라"만 그 순서로 남는다. 남은 두 건의 `id`, `title`, `done: false`, `due`는 요청 전과 같다. 마감일이 있는 진행 중 항목의 `due`도 그대로다. 이어서 할 일을 새로 추가하면 `id`가 지운 ID(위 예에서 1, 3)를 재사용하지 않고 5가 된다.
- **REQ-18**: 완료 항목이 두 건인 상태에서 `DELETE /api/todos/completed`를 보내면 `deleted: 2`이고, 곧바로 같은 요청을 다시 보내면 `200`과 `deleted: 0`이며 `todos`가 바로 앞 응답과 같다. 완료 항목이 하나도 없는 목록(진행 중 한 건만 있는 경우와 빈 목록)에 보내도 `200`과 `deleted: 0`이고 `GET /api/todos` 결과가 요청 전과 같으며, 빈 목록에서는 `todos`가 `[]`다. 응답 본문에는 지운 항목을 되살릴 수 있는 정보(삭제한 할 일 목록이나 복구용 토큰 등)가 담기지 않고 `deleted`와 `todos`만 있으며, 되살리는 API도 없다. 삭제 후 화면이 응답의 `todos`로 목록을 다시 그리는지는 REQ-08의 (나)와 같이 구현 PR에서 사람이 확인한다.

## 위험

- **삭제는 되돌릴 수 없음**: 사용자가 고른 할 일을 바로 지우며 복구 수단이 없습니다(REQ-06, REQ-18). 한 건씩 지우는 버튼은 목록의 각 줄 안에만 둡니다.
- **일괄 삭제는 한 번에 여러 건을 지움(위험도 높음)**: 완료한 할 일을 한 번에 지우므로 잘못 누르면 되돌릴 수 없는 손실이 큽니다. 리더 결정에 따라 위험도를 높음으로 보고, 다음으로 범위를 좁힙니다. ① 대상은 완료된 항목으로만 한정하고 진행 중 항목은 서버에서도 지우지 않습니다(REQ-17). ② 누르기 전에 지워질 개수를 보여 주는 확인 창을 반드시 거칩니다(REQ-16). ③ 지울 것이 없을 때는 버튼을 누를 수 없게 둡니다(REQ-15). 그래도 확인 창에서 "확인"을 누르면 복구할 수 없으므로, 되살리기가 필요해지면 별도 요청으로 다룹니다.
- **확인 창의 개수와 실제로 지워지는 개수가 다를 수 있음**: 확인 창의 개수는 화면이 마지막으로 그린 목록을 기준으로 셉니다. 확인 창이 떠 있는 동안 다른 사람이 완료 상태를 바꾸면 서버가 실제로 지우는 개수와 어긋날 수 있습니다. 서버는 요청 시점의 완료 항목만 지우고 지운 개수(`deleted`)와 남은 목록(`todos`)을 함께 돌려주며, 화면은 그 목록으로 다시 그려 어긋남이 남지 않게 합니다(REQ-18). 개수를 서버에 미리 물어보는 절차는 두지 않습니다.
- **확인 창은 자동 검사로 확인할 수 없음**: 브라우저가 스크립트를 실행해야 확인 창이 뜨는지 알 수 있어, "확인 창이 실제로 뜨고 취소가 동작하는가"는 자동으로 보장되지 않습니다(REQ-16). 문구 템플릿이 HTML 한 곳에 올바른 형태로 있는지는 자동으로 대조하고, 뜨는 동작과 취소 동작은 구현 PR에서 사람이 눌러 보고 확인합니다. 리더가 필수로 요구한 조건이므로 구현 PR의 사람 확인 항목에 빠뜨리지 않고 적습니다.
- **고정 경로와 ID 경로의 충돌**: `/api/todos/completed`는 `/api/todos/{id}`와 같은 모양이라, 경로를 가르는 순서가 틀리면 `completed`가 ID로 해석되어 `404 not_found`가 됩니다. 고정 경로를 먼저 확인하도록 설계에 못 박아 두고(`## 구조`, `## API`), 수용 기준에서 이 경로의 응답을 확인합니다(REQ-15).
- **서버 통신 규격을 이번에 처음 확정**: 이후 작업이 이 규격을 따르게 되므로, 변경이 필요하면 코드부터 바꾸지 않고 문서 PR로 먼저 제안합니다.
- **데이터가 메모리에만 있음**: 서버를 다시 켜거나 배포하면 목록이 사라집니다. 합의된 동작이지만(REQ-09) 실제로 공유해 쓸 때 혼동이 생길 수 있어, 영속 저장이 필요해지면 별도 요청으로 다룹니다.
- **동시 요청**: 여러 사람이 같은 서버를 쓰면 같은 목록을 동시에 고칠 수 있습니다. 저장소를 뮤텍스로 보호하고, 화면은 조작 후 목록을 다시 불러와 어긋남을 줄입니다.
- **화면 동작은 자동 검사로 확인하지 못함**: 브라우저를 띄우는 검사를 쓸 수 없어, 오류 문구가 실제로 화면에 뜨는지와 성공 후 안내가 비워지는지는 자동으로 확인되지 않습니다(REQ-08). 문구 자체는 화면과 서버 양쪽을 같은 표와 대조해 자동으로 맞추고, 남는 실행 시점 동작은 구현 PR에서 사람이 눌러 보고 확인합니다.
- **필터를 자리만 비워 둠**: 나중에 필터를 넣을 때 화면 구조를 다시 고쳐야 할 수 있습니다. 추가 영역과 목록 사이의 한 영역으로 자리를 고정해 변경 범위를 좁혀 둡니다(REQ-10).
- **주고받는 자료 규격이 바뀜**: 할 일 한 건에 `due`가 생기고 `PATCH` 본문이 `done` 외에 `due`도 받습니다(REQ-11, REQ-13). 화면과 서버가 같은 규격을 쓰므로 한쪽만 바꾸면 마감일이 보이지 않거나 저장되지 않을 수 있어, 구현에서 응답 변환과 화면 그리기를 함께 고칩니다. 응답에서 마감일 없음을 키 생략이 아니라 항상 `null`로 담도록 정해 두어 화면이 값을 잘못 읽을 여지를 줄입니다.
- **날짜 입력의 브라우저 차이**: `<input type="date">`를 지원하지 않는 브라우저에서는 글자 입력란으로 보여 사용자가 아무 형식으로나 적을 수 있습니다. 화면에서 값을 고치지 않고 그대로 보내고 서버가 한 곳에서 검증해 `due_invalid` 문구로 안내합니다(REQ-12). 날짜 고르기 UI 자체를 직접 만들지는 않습니다.
- **마감일이 지났는지 알려 주지 않음**: 이번 범위에서는 마감일을 보여 주기만 하고 지난 항목을 강조하지 않아, 사용자가 놓칠 수 있습니다. 요청에서 제외된 항목이므로 별도 이슈로 다루며, 기준 시간대도 그때 함께 정합니다.
- **마감일 순서로 볼 수 없음**: 목록은 추가한 순서로만 보여 주므로(REQ-04, REQ-14) 마감일이 가까운 일을 찾기 어려울 수 있습니다. 정렬과 우선순위는 리더 결정에 따라 마감일 다음 순서로 미뤄 두고 별도 요청으로 다룹니다.
