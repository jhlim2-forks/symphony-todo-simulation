# 설계

## 구조

저장소 루트의 단일 Go 모듈(`module todo`)로 두고, Go 표준 라이브러리와 HTML/CSS/JavaScript만 사용합니다. 외부 모듈과 CDN은 쓰지 않습니다.

- `main.go`: `-listen` 플래그(기본값 `127.0.0.1:8091`)를 받아 HTTP 서버를 띄웁니다. 라우터 구성은 테스트에서 `net/http/httptest`로 바로 쓸 수 있도록 서버 실행과 분리합니다.
- 할 일 저장소: 메모리에만 보관합니다(REQ-09). 추가한 순서를 유지하는 슬라이스와 다음 ID 값을 함께 두고, 동시 요청에 대비해 뮤텍스로 보호합니다. ID는 1부터 1씩 증가하며 삭제한 ID는 재사용하지 않습니다.
- 마감일 보관: 할 일 한 건에 마감일 한 개를 둡니다(REQ-11). 값이 있을 때는 `YYYY-MM-DD` 형식의 표준 문자열로, 없을 때는 "없음"으로 구분해 보관하고(예: `*string` 또는 `*time.Time`), JSON으로 내보낼 때 없으면 `null`이 되게 합니다. 시각·시간대는 보관하지 않습니다.
- 우선순위: 할 일마다 `priority` 값을 하나 가집니다(REQ-15). 허용 값은 `high`, `normal`, `low` 세 개뿐이고, 값 검사와 "높음/보통/낮음" 이름 짝은 한 곳(값 → 순위·이름 표)에서만 정의해 핸들러와 화면이 같은 표를 따릅니다. 정렬에 쓰는 순위는 `high`=0, `normal`=1, `low`=2입니다.
- 목록 순서: 저장소는 추가한 순서를 그대로 보관하고, 목록을 내보낼 때 우선순위 순위를 첫 기준, `id` 오름차순을 두 번째 기준으로 정렬합니다(REQ-04). `id`가 추가한 순서이므로 같은 우선순위 안에서는 추가한 순서가 유지되고, 우선순위를 바꿔도 추가한 순서 자체는 변하지 않습니다(REQ-17). 마감일은 순서에 쓰지 않으므로 마감일을 넣거나 바꾸거나 지워도 순서는 그대로입니다(REQ-14). 정렬은 보관한 슬라이스를 복사한 뒤 수행해 원래 순서를 건드리지 않습니다.
- HTTP 핸들러: `/`는 화면 파일을 제공하고, `/api/todos`와 `/api/todos/{id}`는 JSON API를 제공합니다. 제목 검증(공백 제거, 200자 제한), 마감일 검증(형식과 실제 있는 날짜인지), 우선순위 값 검증은 저장소에 넣기 전에 각각 한 곳에서 수행하며, 추가(`POST`)와 수정(`PATCH`)이 같은 검증 함수를 함께 씁니다(REQ-12, REQ-16, REQ-17).
- `index.html`: 화면 한 파일. 서버가 `/`에서 제공하며 API를 호출해 목록을 다시 그립니다.

처리 흐름: 화면이 `GET /api/todos`로 목록을 받아 그리고, 추가·상태 변경·마감일 변경·우선순위 변경·삭제 후에는 응답을 반영하거나 목록을 다시 불러와 화면과 서버 상태를 일치시킵니다.

## API

요청·응답 형식과 오류 코드는 `docs/requirements.md`의 `## API 계약`을 그대로 따릅니다. 구현에서 정하는 세부 사항은 다음과 같습니다.

- `GET /api/todos`
  - 우선순위가 높은 것부터, 같은 우선순위 안에서는 추가한 순서대로 `todos` 배열을 반환합니다(REQ-04). 목록이 비어 있으면 `{"todos": []}`입니다(`null` 아님).
  - 각 할 일에는 `priority`와 `due`가 언제나 들어갑니다(`due`는 없으면 `null`).
- `POST /api/todos`
  - 본문을 JSON으로 해석하고 `title`을 문자열로 읽습니다. 해석에 실패하거나 `title`이 문자열이 아니면 `400 invalid_json`입니다.
  - `priority`는 생략할 수 있습니다. 없거나 `null`이면 `normal`로 둡니다(REQ-15, REQ-16). 값이 있으면 문자열이어야 하고 `high`/`normal`/`low` 중 하나여야 하며, 그렇지 않으면 `400 invalid_priority`입니다(대소문자나 한국어 이름은 받지 않습니다).
  - `due`도 생략할 수 있습니다. 생략했거나 `null`이면 마감일 없는 할 일로 추가합니다. 문자열이면 아래 마감일 검증을 거치고, 문자열도 `null`도 아닌 값(숫자·객체 등)이면 `400 invalid_json`입니다(REQ-11).
  - 마감일 검증: 길이가 10이고 `YYYY-MM-DD` 모양인지 먼저 확인한 뒤 `time.Parse("2006-01-02", 값)`으로 해석합니다. 해석에 실패하면 `400 due_invalid`입니다. 이 방식은 `2026-02-30`, `2026-13-01`, 평년의 `2026-02-29`처럼 달력에 없는 날짜와 `2026-3-1` 같은 형식 오류를 모두 거절하고, 윤년의 `2024-02-29`는 통과시킵니다(REQ-12).
  - 검사 순서는 `title`(`invalid_json` → `title_blank` → `title_too_long`) 다음에 `priority`(`invalid_priority`), 그다음 `due`(`due_invalid`)이며, 거절한 요청은 목록을 바꾸지 않습니다.
  - `priority`가 문자열이 아닌 값(숫자 등)일 때도 `invalid_priority`로 답하려면, 본문을 한 번에 구조체로 해석하지 않고 `title`·`done`·`priority`·`due`를 `json.RawMessage`로 받아 필드마다 따로 해석합니다. 본문 자체가 JSON이 아닐 때만 `invalid_json`입니다.
  - 제목의 앞뒤 공백(스페이스, 탭, 개행 등)을 제거합니다. 결과가 빈 문자열이면 `400 title_blank`입니다.
  - 제거 후 문자 수를 유니코드 코드 포인트(Go의 룬) 단위로 셉니다(`utf8.RuneCountInString`). 바이트 수로 세지 않으므로 한글·이모지 한 글자도 1자입니다(REQ-03). 200보다 크면 `400 title_too_long`이며, 정확히 200자는 허용합니다. 이어 붙인 이모지는 코드 포인트 수만큼 세며, 이를 한 글자로 묶는 처리는 표준 라이브러리만 쓰는 제약 때문에 하지 않습니다.
  - 성공하면 `201`과 추가된 할 일(`id`, `title`, `done: false`, `priority`, `due`)을 반환합니다.
- `PATCH /api/todos/{id}`
  - 본문에 `done`, `priority`, `due` 중 하나 이상을 담습니다. 본문이 JSON이 아니면 `400 invalid_json`, 세 키가 모두 없으면 `400 nothing_to_update`입니다.
  - `done`을 보냈는데 불리언이 아니면 `400 done_required`, `priority`를 보냈는데 `high`/`normal`/`low`가 아니면 `400 invalid_priority`, `due`에 보낸 날짜가 `POST`와 같은 검증을 통과하지 못하면 `400 due_invalid`입니다. 보내지 않은 값은 그대로 둡니다. 키가 있는지와 값의 형식을 따로 보려면 `POST`와 같이 필드마다 `json.RawMessage`로 받아 해석합니다.
  - `due`에 날짜 문자열이 오면 그 날짜로 바꾸고, `null`이 오면 마감일을 지웁니다. 마감일 변경은 제목·완료 여부·우선순위와 다른 할 일, 그리고 목록 순서를 바꾸지 않습니다(REQ-13, REQ-14).
  - `id`가 정수가 아니거나 해당 할 일이 없으면 `404 not_found`입니다.
  - 성공하면 `200`과 변경된 할 일을 반환합니다. 이미 같은 상태·같은 우선순위·같은 마감일이었다면 그대로 두고 `200`을 반환합니다.
- `DELETE /api/todos/{id}`
  - 성공하면 `204`(본문 없음)입니다. `id`가 정수가 아니거나 해당 할 일이 없으면 `404 not_found`입니다.
- 오류 응답은 모두 `{"error": {"code": ..., "message": ...}}` 형태이며, 오류가 발생한 요청은 목록을 바꾸지 않습니다. 여러 값을 함께 보낸 `PATCH`는 모두 검증한 뒤 적용하므로, 하나라도 거절되면 아무 값도 바뀌지 않습니다.
- 오류 본문은 계약에 정의한 코드와 문구의 조합만 사용합니다. 코드별 한국어 문구를 한 곳(코드 → 문구 표)에서 만들고, 서버 내부 오류 메시지나 요청 본문의 내용을 `message`에 넣지 않습니다. 표에 없는 경로의 `404 not_found`와 정의되지 않은 메서드의 `405 method_not_allowed`도 같은 형식과 문구를 사용합니다.

## UI

`index.html` 한 페이지, 한국어 화면입니다(REQ-08). 위에서 아래로 다음 순서로 배치합니다.

1. 제목 영역: "할 일 목록".
2. 추가 영역: 제목 입력란(안내 문구 "할 일을 입력하세요"), 우선순위 선택(`<select id="new-priority">`), 마감일 입력란, "추가" 버튼. 입력란이 비어 있거나 공백만 있으면 서버에 보내지 않고 "할 일 제목을 입력해 주세요."를 보여 줍니다. 추가에 성공하면 제목과 마감일 입력란을 비웁니다.
   - 길이 판정의 기준은 서버의 유니코드 문자 수(REQ-03)입니다. 화면에서 미리 막을 때도 같은 기준으로 세며(예: `Array.from(제목).length`), 브라우저가 다른 단위로 세는 `maxlength` 속성에는 의존하지 않습니다. 200자를 넘기면 계약의 문구 "할 일 제목은 200자까지 입력할 수 있습니다."를 보여 줍니다.
   - 우선순위 선택에는 "높음 / 보통 / 낮음" 세 항목만 두고 각 항목의 값은 `high` / `normal` / `low`입니다. 항목은 정적 마크업에 적지 않고 스크립트가 아래 `priority-labels` 표의 `order`·`labels`를 읽어 만듭니다. 처음에는 `default`인 "보통"이 선택되어 있고, 추가에 성공하면 다시 "보통"으로 되돌립니다(REQ-15, REQ-16).
   - 마감일 입력란은 `<label>마감일(선택)</label>`과 `<input type="date">`로 둡니다. 이 입력은 값이 있을 때 `YYYY-MM-DD` 문자열을 주므로 계약 형식과 그대로 맞습니다. 비워 두면 `due`를 보내지 않아 마감일 없는 할 일로 추가합니다(REQ-11). 날짜 입력을 지원하지 않는 브라우저에서는 글자 입력란으로 보이므로, 화면은 값을 고치지 않고 그대로 보내고 올바른지는 서버가 판단합니다(REQ-12). 서버가 `due_invalid`로 거절하면 계약의 문구를 오류 안내 영역에 보여 주고 목록은 그대로 둡니다.
   - 추가 요청을 만드는 곳은 `createTodo()` 한 함수입니다. 이 함수가 제목과 함께 `#new-priority`의 값을 읽어 `POST /api/todos`의 `priority`로 담고, 마감일 입력란에 값이 있으면 `due`로 담아 보냅니다(REQ-16).
3. 필터 자리: 추가 영역과 목록 사이에 필터가 들어갈 영역을 비워 둡니다. 이번 구현에서는 아무 요소도 넣지 않으며, 나중에 "전체 / 진행 중 / 완료" 선택을 이 자리에 추가합니다(REQ-10).
4. 목록 영역: 서버가 준 순서(우선순위 높은 것부터, 같은 우선순위는 추가한 순서)대로 각 줄에 완료 체크박스, 우선순위 배지, 제목, 마감일 표시, 우선순위 변경 선택, 마감일 수정 영역, "삭제" 버튼을 놓습니다. 완료된 할 일은 체크 상태로 표시하고 제목에 취소선을 넣습니다. 목록이 비어 있으면 "할 일이 없습니다."를 보여 줍니다.
   - 우선순위 배지(REQ-18): 각 줄의 제목 앞에 `<span class="badge priority-high|priority-normal|priority-low">높음|보통|낮음</span>`을 둡니다. 배지를 만드는 곳은 `priorityBadge(값)` 한 함수이고, 줄을 그리는 `renderTodos()`가 모든 줄에서 이 함수를 불러 배지를 넣습니다. 이 함수는 `classes`의 클래스와 `labels`의 한국어 글자를 함께 넣으며, 클래스 이름과 이름 글자를 함수 안에 다시 적지 않습니다. CSS에서 세 클래스에 서로 다른 배경색과 글자색을 정합니다(`priority-high`: 붉은 계열 `#b3261e` 배경, `priority-normal`: 회색 계열 `#5f6368` 배경, `priority-low`: 푸른 계열 `#1a73e8` 배경, 글자색은 모두 흰색 `#ffffff`). 글자는 마크업에서 넣고 CSS의 `content`로 만들지 않으므로, 글자와 색을 함께 담아 색을 구분하기 어려운 사람도 글자로 알 수 있습니다.
   - 우선순위 변경(REQ-17): 각 줄에 "높음 / 보통 / 낮음" 선택(`<select class="priority-select">`)을 두고 현재 단계가 선택된 상태로 그립니다. 이 선택도 정적 마크업이 아니라 `renderTodos()`가 `priority-labels` 표를 읽어 줄마다 만듭니다. 값을 바꾸면 `changePriority(id, 고른 값)` 한 함수가 `PATCH /api/todos/{id}`에 `{"priority": 고른 값}`을 보내고, 응답을 받은 뒤 `loadTodos()`로 목록을 다시 불러와 새 순서로 그립니다.
   - 마감일 표시: `due`가 있으면 "마감일: 2026-03-01"처럼 날짜를 그대로 보여 주고, `null`이면 "마감일 없음"을 보여 줍니다(REQ-14). 마감일이 지났는지에 따라 달리 표시하지는 않습니다(범위 밖).
   - 마감일 수정: 각 줄에 `<input type="date">`와 "마감일 지우기" 버튼을 둡니다. 날짜를 고르면 그 줄의 할 일에 `PATCH {"due": "YYYY-MM-DD"}`를, "마감일 지우기"를 누르면 `PATCH {"due": null}`을 보냅니다(REQ-13). 마감일이 있는 할 일은 입력란의 초기값을 현재 마감일로 채우고, 없는 할 일은 비워 둡니다. "마감일 지우기" 버튼은 마감일이 있는 줄에만 둡니다.
   - 화면 조작은 언제나 한 가지 값만 담아 `PATCH`를 보냅니다(완료 체크박스는 `done`, 우선순위 선택은 `priority`, 마감일 수정은 `due`). 따라서 `nothing_to_update`는 화면 조작에서는 생기지 않습니다.
   - 우선순위 값과 화면 이름·배지 클래스의 짝도 오류 문구와 같은 방식으로 `index.html`에 JSON 한 덩어리로 한 곳만 둡니다. 스크립트와 선택 항목은 이 요소를 읽어 만들고, 같은 이름을 다른 곳에 다시 적지 않습니다.

     ```html
     <script type="application/json" id="priority-labels">
     {
       "default": "normal",
       "order": ["high", "normal", "low"],
       "labels": {
         "high": "높음",
         "normal": "보통",
         "low": "낮음"
       },
       "classes": {
         "high": "priority-high",
         "normal": "priority-normal",
         "low": "priority-low"
       }
     }
     </script>
     ```
5. 오류 안내 영역: 목록 아래 한 곳에 `id="error"`인 빈 요소로 둡니다. 보여 줄 문구는 다음 기준으로 정합니다.
   - 응답 본문이 계약의 오류 형식(`error.code`, `error.message`)이고 `code`가 계약에 정의된 값이면, 그 코드에 해당하는 계약의 한국어 문구를 보여 줍니다.
   - 그 밖의 경우(본문 형식이 다름, 정의되지 않은 코드, 본문을 JSON으로 해석할 수 없음, 통신 실패)에는 화면이 가진 한국어 기본 문구 "요청을 처리할 수 없습니다. 잠시 후 다시 시도해 주세요."를 보여 줍니다.
   - 어느 경우에도 응답 본문을 그대로 덧붙이거나 이어서 보여 주지 않습니다. 이어지는 요청이 성공하면 이 영역을 비웁니다.
   - 위 기준 중 "어떤 코드에 어떤 문구를 쓰는가"는 기계가 그대로 읽어 대조할 수 있는 형태로 둡니다. `index.html`에 아래와 같이 JSON 한 덩어리를 담은 요소를 한 곳만 두고, 스크립트는 화면을 그리기 전에 이 요소를 읽어 `ERROR_MESSAGES`와 `DEFAULT_ERROR_MESSAGE`로 씁니다. 같은 문구를 스크립트 안에 다시 적지 않습니다.

     ```html
     <script type="application/json" id="error-messages">
     {
       "default": "요청을 처리할 수 없습니다. 잠시 후 다시 시도해 주세요.",
       "codes": {
         "invalid_json": "요청 형식이 올바르지 않습니다.",
         "title_blank": "할 일 제목을 입력해 주세요.",
         "title_too_long": "할 일 제목은 200자까지 입력할 수 있습니다.",
         "done_required": "완료 여부(done)를 true 또는 false로 보내 주세요.",
         "invalid_priority": "우선순위는 높음, 보통, 낮음 중에서 골라 주세요.",
         "due_invalid": "마감일은 2026-03-01처럼 실제로 있는 날짜로 입력해 주세요.",
         "nothing_to_update": "바꿀 내용을 보내 주세요. 완료 여부(done), 우선순위(priority), 마감일(due) 중 하나가 필요합니다.",
         "not_found": "해당 할 일을 찾을 수 없습니다.",
         "method_not_allowed": "허용되지 않은 요청 방식입니다."
       }
     }
     </script>
     ```

   - 문구 표시는 `showError(응답)` 한 함수만, 비우기는 `clearError()` 한 함수만 담당합니다. `showError`는 `ERROR_MESSAGES`에서 찾은 문구를, 찾지 못하면 `DEFAULT_ERROR_MESSAGE`를 오류 영역의 텍스트로 넣습니다(응답 본문을 덧붙이지 않음). 목록 불러오기, 추가, 상태 변경, 삭제의 성공 처리 경로는 모두 `clearError()`를 호출합니다.
   - 확인 방법과 그 한계: 프로젝트 제약상 테스트는 브라우저 없이 `net/http/httptest`로만 실행하므로, 화면 동작을 눌러 보며 확인하는 자동 검사는 두지 않습니다. 대신 ① 위 JSON 덩어리는 서버가 `/`에서 돌려주는 본문에서 꺼내 `encoding/json`으로 해석한 뒤 계약의 코드·문구와 정확히 같은지 대조하고, ② 서버가 실제로 돌려주는 오류 응답의 코드·문구도 같은 기준으로 대조해, 화면에 보일 문구와 서버가 보내는 문구가 어긋나지 않음을 자동으로 보장합니다. ③ 그 문구가 실제 브라우저 화면에 그려지는지, 성공 후 안내가 비워지는지 같은 실행 시점 동작은 자동으로 확인하지 못하므로, 구현 PR에서 사람이 한 번 눌러 보고 확인하는 항목으로 둡니다(수용 기준의 REQ-08 참고).

조작은 체크박스 변경 시 `PATCH`, 줄의 우선순위 선택 변경 시 `PATCH`, 날짜 입력이나 "마감일 지우기" 사용 시 `PATCH`, "삭제" 클릭 시 `DELETE`를 호출하고, 응답을 받아 목록을 다시 그립니다. 제목은 그대로 텍스트로 표시해 HTML로 해석되지 않게 합니다. 우선순위를 바꾸면 순서가 달라질 수 있으므로 변경 후에는 목록을 다시 불러옵니다.

## 수용 기준

이미 구현된 요구사항(REQ-01~REQ-03, REQ-05~REQ-09, REQ-11~REQ-14)의 기준은 `main`에 있는 승인된 테스트(`app_test.go`)로 그대로 확인합니다. 이 문서 변경은 동작 정의만 고치므로 코드와 테스트 파일은 `main`의 승인된 상태를 그대로 두며, 병합 과정에서 그 테스트 파일이 빠졌다면 되살린 뒤 검사합니다. 구현 예정인 요구사항(REQ-04, REQ-10, REQ-15~REQ-18)의 테스트는 우선순위를 만드는 구현 PR에서 함께 붙입니다. 특히 REQ-04는 순서 규칙이 바뀌어 다시 구현 예정이 되었으므로, 기존 테스트 주석에 남은 REQ-04 참조는 구현 PR에서 빼고 새 순서를 확인하는 테스트에서 다시 참조합니다(`docs/README.md`의 테스트 연결 규칙).

- **REQ-01**: 빈 목록에서 `POST /api/todos`에 `{"title": "장보기"}`를 보내면 `201`과 함께 `id`가 1, `title`이 `"장보기"`, `done`이 `false`, `due`가 `null`인 할 일을 받고, 이어진 `GET /api/todos`에 그 할 일이 보인다. 한 번 더 추가하면 `id`가 2가 된다. 응답에 `priority`가 함께 들어가는지는 REQ-15에서 확인한다.
- **REQ-02**: `{"title": "  장보기  "}`로 추가하면 저장된 `title`이 `"장보기"`다. `{"title": ""}`와 `{"title": "   "}`는 `400 title_blank`이고, 이후 `GET /api/todos`의 목록 길이가 늘지 않는다.
- **REQ-03**: 영문자 200자 제목은 `201`로 추가되고, 201자 제목은 `400 title_too_long`이며 목록이 늘지 않는다. 한글 "가"를 200번 반복한 제목(바이트로는 600바이트)도 `201`로 추가되고 저장된 `title`의 문자 수가 200이며, 201번 반복한 제목은 `400 title_too_long`이고 `GET /api/todos`의 목록 길이가 늘지 않는다. 이모지 "🙂" 200개로 된 제목도 같은 기준으로 `201`로 추가된다.
- **REQ-04**: 우선순위를 주지 않고 "가", "나", "다"를 순서대로 추가하면 `GET /api/todos`의 순서가 "가", "나", "다"다. "가"를 완료로 바꾸고 다시 해제해도 순서가 그대로다. 이어서 "라"(낮음), "마"(높음), "바"(높음)를 차례로 추가하면 순서가 "마", "바", "가", "나", "다", "라"다. 즉 높음이 먼저, 그다음 보통, 마지막이 낮음이며 같은 우선순위 안에서는 추가한 순서다.
- **REQ-05**: 추가한 할 일에 `PATCH {"done": true}`를 보내면 `200`과 `done: true`를 받고 목록에도 반영된다. 이어서 `{"done": false}`를 보내면 `done: false`가 된다. `{"done": true}`를 두 번 보내도 `200`이고 `done: true`를 유지한다.
- **REQ-06**: 세 건 중 두 번째를 `DELETE`하면 `204`를 받고, `GET /api/todos`에는 첫 번째와 세 번째가 원래 순서와 완료 상태로 남는다. 같은 ID를 다시 `DELETE`하면 `404 not_found`다.
- **REQ-07**: 없는 ID(예: 999)와 정수가 아닌 ID(예: `abc`)로 `PATCH` 또는 `DELETE`를 보내면 `404 not_found`이고, `GET /api/todos` 결과가 요청 전과 같다.
- **REQ-08**: 브라우저를 띄우는 검사는 프로젝트 제약상 둘 수 없으므로, 확인할 수 있는 범위를 아래와 같이 나눠 둔다.

  (가) 자동 검사로 확인하는 것
  - `GET /`이 `200`과 HTML을 반환하고, 그 HTML에 제목 입력란, 마감일 입력란, "추가" 버튼, 목록 영역, 오류 안내 영역(`id="error"`, 처음에는 빈 상태)이 있으며 화면 문구가 한국어다. 우선순위 선택이 추가 영역에 있는지는 REQ-16에서 확인한다.
  - HTML에서 `id="error-messages"`인 JSON 요소를 꺼내 `encoding/json`으로 해석하면, `codes`가 지금 승인되어 동작 중인 여덟 코드 `invalid_json`, `title_blank`, `title_too_long`, `done_required`, `due_invalid`, `nothing_to_update`, `not_found`, `method_not_allowed`를 키로 가지며 각 값이 계약의 한국어 문구("요청 형식이 올바르지 않습니다.", "할 일 제목을 입력해 주세요.", "할 일 제목은 200자까지 입력할 수 있습니다.", "완료 여부(done)를 true 또는 false로 보내 주세요.", "마감일은 2026-03-01처럼 실제로 있는 날짜로 입력해 주세요.", "바꿀 내용을 보내 주세요. 완료 여부(done) 또는 마감일(due)이 필요합니다.", "해당 할 일을 찾을 수 없습니다.", "허용되지 않은 요청 방식입니다.")와 글자 그대로 같다. `default`는 "요청을 처리할 수 없습니다. 잠시 후 다시 시도해 주세요."다. 우선순위를 만들면서 더해지는 `invalid_priority`와 바뀌는 `nothing_to_update` 문구는 REQ-16에서 확인한다.
  - 서버가 돌려주는 오류 응답의 코드·문구가 같은 표와 글자 그대로 일치한다. 예: `POST /api/todos`에 JSON이 아닌 본문을 보내면 `{"error": {"code": "invalid_json", "message": "요청 형식이 올바르지 않습니다."}}`, 정의되지 않은 메서드 요청(예: `PUT /api/todos`)은 `405`와 `{"error": {"code": "method_not_allowed", "message": "허용되지 않은 요청 방식입니다."}}`를 반환한다. 이로써 화면에 보일 문구와 서버가 보내는 문구가 어긋나지 않음을 보장한다.
  - HTML에 적힌 오류 문구는 위 JSON 요소 안의 문구뿐이고, 스크립트 안에 같은 문구를 다시 적은 곳이 없다.

  (나) 자동으로 확인하지 않는 것(확인 범위 밖, 구현 PR에서 사람이 눌러 보고 확인)
  - 오류가 났을 때 그 문구가 실제로 오류 안내 영역에 그려지는지.
  - 계약에 없는 응답·해석 실패·통신 실패일 때 기본 문구가 그려지는지.
  - 목록 불러오기, 추가, 상태 변경, 삭제가 성공한 뒤 오류 안내가 비워지는지.

  (나)는 브라우저가 스크립트를 실행해야 알 수 있어 자동 검사로 다루지 않는다. 대신 틀릴 여지를 줄이려고 화면 쪽 구현을 다음으로 고정하고, 이 구조가 지켜졌는지는 구현 PR의 코드 검토에서 확인한다: 문구를 넣는 곳은 `showError` 한 곳, 비우는 곳은 `clearError` 한 곳이며, 응답 본문을 문구에 이어 붙이지 않고, 네 가지 성공 처리 경로가 모두 `clearError()`를 호출한다.
- **REQ-09**: 저장소를 새로 만든 상태(서버 재시작과 같음)에서 `GET /api/todos`가 `200`과 `{"todos": []}`를 반환한다.
- **REQ-10**: `index.html`에서 필터가 들어갈 영역이 추가 영역과 목록 영역 사이에 한 곳 있고, 그 안에 "전체 / 진행 중 / 완료"를 고르는 요소가 없어 목록을 걸러 볼 수 없다. `GET /api/todos`는 필터 조건을 받지 않고 언제나 전체 목록을 REQ-04의 순서로 반환한다.
- **REQ-11**: `POST /api/todos`에 `{"title": "장보기", "due": "2026-03-01"}`을 보내면 `201`과 `due`가 `"2026-03-01"`인 할 일을 받고, `GET /api/todos`에도 같은 값이 보인다. `{"title": "청소"}`처럼 `due`를 생략하거나 `{"title": "청소", "due": null}`로 보내면 `201`이고 응답과 목록의 `due`가 `null`이다(키가 빠지지 않는다). `due`에 숫자나 객체를 보내면 `400 invalid_json`이고 목록이 늘지 않는다.
- **REQ-12**: `POST /api/todos`에 `due`를 `"2026-02-30"`, `"2026-13-01"`, `"2026-02-29"`, `"2026-3-1"`, `"03/01/2026"`, `"2026-03-01T10:00:00Z"`로 각각 보내면 모두 `400 due_invalid`이고 `GET /api/todos`의 목록 길이가 늘지 않는다. `"2024-02-29"`와 `"2020-01-01"`(과거 날짜)은 `201`로 추가되고 응답의 `due`가 보낸 값과 같다. 마감일이 `"2026-03-01"`인 할 일에 `PATCH {"due": "2026-02-30"}`을 보내면 `400 due_invalid`이고 그 할 일의 `due`는 `"2026-03-01"`로 남는다.
- **REQ-13**: `due`가 `null`인 할 일에 `PATCH {"due": "2026-03-01"}`을 보내면 `200`과 `due: "2026-03-01"`을 받는다. 이어서 `PATCH {"due": "2026-04-02"}`를 보내면 `due`가 `"2026-04-02"`로 바뀌고, `PATCH {"due": null}`을 보내면 `due`가 `null`이 된다. 이 과정에서 그 할 일의 `title`과 `done`은 바뀌지 않고 다른 할 일의 `due`도 그대로다. 마감일만 보낸 `PATCH`는 `done`을 바꾸지 않고, `done`만 보낸 `PATCH`는 `due`를 바꾸지 않는다. 마감일 변경이 `priority`를 건드리지 않는지는 REQ-17에서 확인한다. `PATCH {}`는 `400 nothing_to_update`이고 아무것도 바뀌지 않으며, 없는 ID로 보낸 `PATCH {"due": "2026-03-01"}`은 `404 not_found`다.
- **REQ-14**: `GET /api/todos`의 각 할 일에 `due` 항목이 있고, 마감일이 있는 할 일은 날짜 문자열, 없는 할 일은 `null`이다. `GET /`이 돌려주는 HTML에 각 줄의 마감일을 보여 줄 자리와 마감일이 없을 때 쓰는 한국어 문구("마감일 없음"), 마감일을 바꾸는 날짜 입력란, "마감일 지우기" 버튼이 있다. 세 건을 추가한 뒤 두 번째 할 일에 마감일을 넣고 바꾸고 지워도 `GET /api/todos`의 순서가 그 전과 같다. 우선순위를 섞은 목록에서도 마감일 변경이 순서를 바꾸지 않는지는 REQ-17에서 함께 확인한다. 각 줄에 실제로 마감일이 그려지는지는 REQ-08의 (나)와 같은 이유로 구현 PR에서 사람이 확인한다.
- **REQ-15**: `priority` 없이 추가한 할 일의 `priority`가 `"normal"`이고, `{"title": "가", "priority": null}`로 추가해도 `"normal"`이다. `{"title": "가", "priority": "high"}`는 `"high"`로 저장된다. `"HIGH"`, `"높음"`, `"urgent"`, `1`처럼 세 값이 아닌 값은 `400 invalid_priority`이고 `GET /api/todos`의 목록 길이가 늘지 않는다. 추가 응답, 변경 응답, 목록의 모든 할 일에 `priority` 키가 언제나 들어간다(REQ-01에서 확인하던 `priority: "normal"`도 여기서 함께 확인한다).
- **REQ-16**: 확인 범위를 REQ-08과 같은 방식으로 나눠 둔다.

  (가) 자동 검사로 확인하는 것
  - `GET /`이 돌려주는 HTML에 `id="new-priority"`인 `<select>`가 추가 영역(제목 입력란과 "추가" 버튼 사이) 안에 한 곳만 있고, 정적 마크업 안에는 `<option>`이 적혀 있지 않다. 항목은 스크립트가 `priority-labels`를 읽어 만든다.
  - `id="priority-labels"`인 JSON 요소를 `encoding/json`으로 해석하면 `default`가 `"normal"`, `order`가 `["high","normal","low"]`, `labels`가 `high`→"높음", `normal`→"보통", `low`→"낮음"이고, `labels`와 `classes`의 키가 `order`의 세 값과 정확히 같다(빠지거나 남는 키가 없다). 처음 선택되는 단계는 `default`가 정하므로 "보통"이다.
  - HTML 전체에서 `new-priority`라는 문자열은 두 곳, 즉 선택 요소의 `id`와 그 값을 읽어 추가 요청을 만드는 스크립트 코드에만 나타난다(이 `id`로 꾸미는 CSS 규칙은 두지 않는다). 이로써 추가 요청을 만드는 코드가 선택 요소의 값을 읽고, 그 일을 하는 곳이 하나뿐임을 확인한다.
  - 서버 쪽은 세 값(`high`/`normal`/`low`)으로 각각 추가하면 `201`과 보낸 값이 그대로 담긴 할 일을 반환하고, 이어진 `GET /api/todos`의 그 할 일도 같은 값을 가진다. `priority`를 생략하면 `normal`로 추가된다. 세 값이 아닌 값은 `400 invalid_priority`로 거절해 목록을 바꾸지 않는다.
  - `id="error-messages"` JSON에 `invalid_priority` 코드가 더해져 아홉 코드가 되고, 그 문구가 "우선순위는 높음, 보통, 낮음 중에서 골라 주세요."이며, `nothing_to_update` 문구가 "바꿀 내용을 보내 주세요. 완료 여부(done), 우선순위(priority), 마감일(due) 중 하나가 필요합니다."로 바뀐다. 서버가 돌려주는 두 오류의 문구도 이 표와 글자 그대로 같다(REQ-08의 대조 방식 그대로이며, 우선순위를 만든 뒤의 상태를 확인한다).

  (나) 자동으로 확인하지 않는 것(확인 범위 밖, 구현 PR에서 사람이 눌러 보고 확인)
  - 선택 항목 세 개가 "높음 / 보통 / 낮음"으로 그려지고 처음에 "보통"이 선택되어 보이는지.
  - 선택을 바꿔 "추가"를 누르면 고른 값이 실제로 `POST /api/todos`의 `priority`에 담겨 전송되는지, 추가에 성공한 뒤 선택이 다시 "보통"으로 돌아가는지.

  (나)는 브라우저가 스크립트를 실행해야 알 수 있어 REQ-08의 (나)와 같은 이유로 자동 검사로 다루지 않는다. 대신 화면 쪽 구현을 다음으로 고정하고 구현 PR의 코드 검토에서 확인한다: 추가 요청을 만드는 곳은 `createTodo()` 한 함수뿐이고, 이 함수가 `#new-priority`의 값을 읽어 본문의 `priority`로 담으며, 성공 처리에서 선택을 `priority-labels`의 `default`로 되돌린다.
- **REQ-17**: 확인 범위를 REQ-08과 같은 방식으로 나눠 둔다.

  (가) 자동 검사로 확인하는 것
  - 보통으로 추가한 할 일에 `PATCH {"priority": "high"}`를 보내면 `200`과 `priority: "high"`를 받고 `title`·`done`·`due`·`id`는 그대로다. 같은 값으로 두 번 보내도 `200`이고 값이 유지된다.
  - "가"(보통), "나"(보통), "다"(보통)를 추가한 뒤 "다"를 높음으로 바꾸면 `GET /api/todos`의 순서가 "다", "가", "나"가 되고, "다"를 다시 보통으로 바꾸면 순서가 "가", "나", "다"로 돌아온다. 즉 화면이 변경 후 다시 불러올 때 서버가 REQ-04의 새 순서를 돌려준다. 이때 `PATCH` 응답의 할 일과 이어진 `GET /api/todos` 안의 같은 `id` 할 일의 `priority`·`title`·`done`·`due`가 서로 같다.
  - `PATCH {"priority": "urgent"}`는 `400 invalid_priority`, `PATCH {}`는 `400 nothing_to_update`이며 두 경우 모두 `GET /api/todos` 결과가 요청 전과 같다. `PATCH {"done": true, "priority": "low"}`를 보내면 두 값이 함께 바뀌고, 없는 ID로 보내면 `404 not_found`다.
  - 우선순위를 섞어 세 건을 추가한 뒤 한 건의 마감일을 넣고 바꾸고 지워도 그 할 일의 `priority`가 그대로이고 `GET /api/todos`의 순서도 REQ-04 기준의 처음 순서와 같다(REQ-13, REQ-14의 마감일 동작이 우선순위를 건드리지 않음을 확인한다).
  - `GET /`의 정적 마크업에는 `class="priority-select"`인 요소가 없다. 줄마다의 선택은 스크립트가 `priority-labels`를 읽어 만들며, 스크립트에서 `priority-select` 클래스를 붙이는 곳은 한 곳뿐이다(CSS 규칙은 세지 않는다).

  (나) 자동으로 확인하지 않는 것(확인 범위 밖, 구현 PR에서 사람이 눌러 보고 확인)
  - 줄의 우선순위 선택이 현재 단계로 선택된 상태로 그려지는지.
  - 선택을 바꾸면 그 값이 `PATCH /api/todos/{id}`의 `priority`에 담겨 전송되고, 응답을 받은 뒤 목록이 새 순서로 다시 그려지는지.

  (나)는 REQ-08의 (나)와 같은 이유로 자동 검사로 다루지 않는다. 대신 화면 쪽 구현을 다음으로 고정하고 구현 PR의 코드 검토에서 확인한다: 줄의 우선순위 변경을 보내는 곳은 `changePriority(id, 값)` 한 함수뿐이고, 이 함수가 고른 값을 본문의 `priority`로 담아 `PATCH`를 보낸 뒤 `loadTodos()`를 호출하며, 목록을 그리는 곳은 `renderTodos()` 한 곳이다.
- **REQ-18**: 확인 범위를 REQ-08과 같은 방식으로 나눠 둔다.

  (가) 자동 검사로 확인하는 것
  - `GET /`의 HTML에 `.priority-high`, `.priority-normal`, `.priority-low` CSS 규칙이 각각 있고, 세 규칙의 배경색 값이 서로 다르며, 각 규칙이 배경색과 글자색을 함께 정한다.

  - 정적 마크업에는 배지 요소(`class`에 `badge`를 가진 요소)가 없다. 배지는 스크립트가 줄마다 만들며, 스크립트에서 `badge` 클래스를 붙이는 곳은 한 곳뿐이다(CSS의 `.badge` 규칙은 세지 않는다).

  (나) 자동으로 확인하지 않는 것(확인 범위 밖, 구현 PR에서 사람이 눌러 보고 확인)
  - 배지가 목록의 각 줄에 실제로 그려지는지, 그리고 그 줄의 단계에 맞는 한국어 글자와 색이 함께 보이는지.

  (나)는 브라우저가 스크립트를 실행해야 알 수 있어 REQ-08의 (나)와 같은 이유로 자동 검사로 다루지 않는다. 대신 화면 쪽 구현을 다음으로 고정하고 구현 PR의 코드 검토에서 확인한다: 배지를 만드는 곳은 `priorityBadge(값)` 한 함수뿐이고, 이 함수가 그 값의 `classes` 클래스와 `labels` 글자를 함께 넣으며, 줄을 그리는 `renderTodos()`가 모든 줄에서 이 함수를 불러 배지를 넣는다.

## 위험

- **삭제는 되돌릴 수 없음**: 사용자가 고른 할 일을 바로 지우며 복구 수단이 없습니다. 첫 버전에서는 삭제 버튼을 목록의 각 줄 안에만 두고 일괄 삭제를 제공하지 않아 잘못 누를 범위를 줄입니다(REQ-06).
- **서버 통신 규격을 이번에 처음 확정**: 이후 작업이 이 규격을 따르게 되므로, 변경이 필요하면 코드부터 바꾸지 않고 문서 PR로 먼저 제안합니다.
- **데이터가 메모리에만 있음**: 서버를 다시 켜거나 배포하면 목록이 사라집니다. 합의된 동작이지만(REQ-09) 실제로 공유해 쓸 때 혼동이 생길 수 있어, 영속 저장이 필요해지면 별도 요청으로 다룹니다.
- **동시 요청**: 여러 사람이 같은 서버를 쓰면 같은 목록을 동시에 고칠 수 있습니다. 저장소를 뮤텍스로 보호하고, 화면은 조작 후 목록을 다시 불러와 어긋남을 줄입니다.
- **주고받는 자료 규격이 한 번 더 늘어남**: 할 일 한 건에 `due`와 `priority`가 함께 들어가고 `PATCH` 본문이 세 가지 값을 받습니다(REQ-11, REQ-13, REQ-15, REQ-17). 화면과 서버가 같은 규격을 쓰므로 한쪽만 바꾸면 값이 보이지 않거나 저장되지 않을 수 있어, 구현에서 응답 변환과 화면 그리기를 함께 고칩니다. 응답에서 마감일 없음을 키 생략이 아니라 항상 `null`로 담도록 정해 두어 화면이 값을 잘못 읽을 여지를 줄입니다.
- **날짜 입력의 브라우저 차이**: `<input type="date">`를 지원하지 않는 브라우저에서는 글자 입력란으로 보여 사용자가 아무 형식으로나 적을 수 있습니다. 화면에서 값을 고치지 않고 그대로 보내고 서버가 한 곳에서 검증해 `due_invalid` 문구로 안내합니다(REQ-12). 날짜 고르기 UI 자체를 직접 만들지는 않습니다.
- **마감일이 지났는지 알려 주지 않음**: 이번 범위에서는 마감일을 보여 주기만 하고 지난 항목을 강조하지 않아, 사용자가 놓칠 수 있습니다. 요청에서 제외된 항목이므로 별도 이슈로 다루며, 기준 시간대도 그때 함께 정합니다.
- **화면 동작은 자동 검사로 확인하지 못함**: 브라우저를 띄우는 검사를 쓸 수 없어, 오류 문구가 실제로 화면에 뜨는지와 성공 후 안내가 비워지는지(REQ-08), 마감일이 각 줄에 그려지는지(REQ-14), 고른 우선순위가 실제로 전송되는지(REQ-16, REQ-17), 배지가 각 줄에 그려지는지(REQ-18)는 자동으로 확인되지 않습니다. 대신 ① 문구·이름·클래스는 화면과 서버 양쪽을 같은 표와 대조하고, ② 화면이 이 표만 읽어 쓰는지(같은 값을 다른 곳에 다시 적지 않았는지)와 필요한 요소가 제 자리에 있는지를 서버가 돌려주는 HTML에서 자동으로 확인하며, ③ 남는 실행 시점 동작은 함수를 한 곳으로 고정해 코드 검토로 보고 구현 PR에서 사람이 눌러 보고 확인합니다.
- **필터를 자리만 비워 둠**: 나중에 필터를 넣을 때 화면 구조를 다시 고쳐야 할 수 있습니다. 추가 영역과 목록 사이의 한 영역으로 자리를 고정해 변경 범위를 좁혀 둡니다(REQ-10).
- **목록 순서 규칙이 바뀜(위험도 높음)**: 먼저 합의한 "추가한 순서" 규칙을 우선순위 우선 규칙으로 고치므로(REQ-04), 이 규칙을 전제로 한 설명과 수용 기준이 함께 바뀝니다. 순서를 정하는 곳을 목록을 내보내는 한 곳으로만 두고, 저장소에는 추가한 순서를 그대로 남겨 같은 우선순위 안의 순서가 흔들리지 않게 합니다.
- **마감일과 우선순위 정렬의 결합**: 마감일 변경은 우선순위 정렬에 영향을 주지 않고(REQ-13, REQ-14), 우선순위 변경은 같은 단계 안의 추가 순서를 유지합니다(REQ-04, REQ-17). 마감일로 정렬하거나 걸러 보는 것은 범위 밖입니다.
- **우선순위를 바꾸면 줄이 움직임**: 사용자가 보던 항목이 목록의 다른 자리로 이동해 혼동할 수 있습니다. 변경 후 목록을 다시 불러와 서버와 같은 순서로만 그리고, 순서를 사용자가 직접 바꾸는 기능은 이번 범위 밖으로 둡니다(REQ-17).
- **색만으로 구분하면 알아보기 어려움**: 색 구분이 어려운 사용자나 흑백 화면에서는 색만 쓴 표시를 읽을 수 없습니다. 배지에 "높음/보통/낮음" 글자를 함께 넣어 글자만으로도 알 수 있게 하고, 색 값은 설계에 한 벌만 정해 둡니다(REQ-18).
- **값 이름이 두 벌(영문 값과 한국어 이름)**: API는 `high`/`normal`/`low`, 화면은 "높음/보통/낮음"을 쓰므로 짝이 어긋날 수 있습니다. 짝을 `index.html`의 JSON 한 곳과 서버의 표 한 곳에만 두고, 자동 검사로 두 곳을 대조합니다(REQ-16, REQ-18).
